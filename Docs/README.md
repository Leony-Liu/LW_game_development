# LW_game_development


# 项目概览

本文档是项目的快速入口，面向：

- 开发者；
- Web GPT；
- Desktop Codex；
- 其他参与项目开发的 AI 或人员。

它用于快速恢复项目上下文，包括：

- 项目是什么；
- 当前开发环境；
- 当前开发阶段；
- 当前主要目标；
- 当前阻塞问题；
- 下一步开发方向；
- 人与 AI 如何协作推进项目。

本文档描述的是**当前项目状态摘要**。

当需要确认实际实现时，应以：

- 真实工作区文件；
- Godot Editor 状态；
- Runtime 行为；

作为最终事实来源。


# AI 协作入口规则

本项目所有 AI 协作必须首先遵守：

```

```

它定义：

- AI 如何理解项目；
- AI 如何读取文档；

- AI 如何验证结果；
- AI 如何与开发者协作。

其他项目文档用于提供领域信息，但不能覆盖 `AGENTS.md` 中定义的 AI 工作规则。

文档职责关系：

```

    ↓
```

- `/AGENTS.md`

# AI 协作工作流

本项目采用：

```
需求讨论与规划

        ↓

生成实现任务

        ↓

Codex 执行

        ↓

验证与反馈
```

的双阶段 AI 协作模式。


目标：

当开启新的 Web GPT 对话、新模型会话，或者新的 Desktop Codex 工作环境时，只需要提供项目文档和当前任务，即可快速恢复一致的项目理解，并继续产生符合项目方向的实现。

# 协作原则


## 用户负责

用户负责：

- 最终设计决策；
- 未确定需求确认；
- 项目方向控制；
- 实现结果验收。


AI 不应该替代用户决定：

- 未设计玩法；
- 未确认规则；
- 未确认架构变化。


## AI 负责

AI 负责：

- 理解已有信息；
- 发现不确定点；
- 提供实现方案；
- 执行明确任务；
- 验证实际结果。


目标不是替代开发者，而是让人和 AI 可以基于相同项目理解持续协作。

# 项目概况

`LW_game_development` 是一个以：

- 第一人称程序生成远征；
- 逻辑时间轴卡牌战斗；
- "武器即牌组"构筑；

为核心方向的游戏项目。

# 当前开发阶段

项目当前在已有远征核心玩法的基础上，开始推进 **基地（Base）与远征（Expedition）之间的应用级流程**。

当前主菜单已具备“开始游戏”（进入 `BaseSystem/Base.tscn`）和“退出游戏”；菜单信号、Base 加载和退出已通过限定运行验证。新增 `WeaponData` 仅含静态元数据示例，卡牌实例 UID 已传入 Battle runtime；基地整备、Base-to-Expedition 和跨战斗数据写回仍未实现。完整验证范围见 `ARCHITECTURE.md` 第 12 节补充记录。


## 既有远征核心目标

此前阶段的基础目标是完成远征系统最基础的可运行闭环：

```
地图生成

    ↓

触发战斗

    ↓

进行战斗

    ↓

结束战斗

    ↓

继续探索
```


既有核心流程仍以以下交互为基础：

```
World ↔ Battle
```

本阶段不替代或重写这条既有流程；后续改动应在需要时对受影响的远征流程进行回归验证。


## 当前阶段目标：基地与远征循环

根据目前的 Godot Editor 状态，已经新建了一个名为 `Base` 的场景；当前截图中的场景树可见 `Field` 和 `Interactive items` 子节点。此记录仅表示基地场景已开始搭建，不代表基地交互、整备功能或场景切换已经实现或通过验证。实际文件路径、节点接线与运行状态仍以真实工作区和运行结果为准。

当前阶段计划逐步实现以下目标：

1. **基地整备：** 玩家能够编辑武器及其绑定的牌组，延续项目“武器即牌组”的核心方向。
2. **进入远征：** 玩家能够从基地进入现有远征流程。
3. **死亡后返回基地：** 当前设计目标是暂时只有玩家在远征中死亡后才能退出远征；死亡结束流程后返回基地。暂不把主动退出远征作为本阶段已确定的功能。
4. **整备配置接入远征：** 基地中编辑的武器与牌组需要在进入远征后真正影响远征使用的玩家/战斗输入，而不能只停留在整备界面中。

预期的整体流程方向：

```
Base
  ↓
编辑武器及其绑定牌组
  ↓
进入 Expedition
  ↓
继续既有的 World ↔ Battle 流程
  ↓
玩家在远征中死亡
  ↓
返回 Base
```

以上内容是当前阶段目标摘要，不表示这些功能已经完成，也不提前决定具体实现方案。


## 实现前的设计讨论范围

开始编写实现任务前，将逐项讨论并确认需求，包括但不限于：

- 玩家如何在基地中移动、交互并打开整备功能；
- 基地的画面内容、整备界面与其他 UI 的布局和操作方式；
- 武器与牌组的具体关系、可编辑内容及操作规则；
- 基地进入远征时，整备配置如何交给现有远征系统并被实际使用；
- 玩家死亡、远征结束、返回基地时的流程与状态处理；
- 基地场景需要新增哪些模型、交互物件或其他场景节点，以及它们的外观和用途；
- 对应的代码职责、数据流、场景切换方式和验证要求。

上述细节目前均不应仅凭 README 推定为已确定设计。交互方式、UI 视觉、模型造型、节点结构、代码架构与具体数据结构，都应在后续讨论中确认后再形成 Codex 实现任务。


## 当前阶段推进顺序

1. 更新 README，记录当前进度、目标与未决设计。
2. 逐项讨论并确认玩法交互、UI/画面、场景模型、数据流和代码实现边界。
3. 形成范围明确的英文 Codex 任务说明。
4. 按确认后的方案增量实现，并按任务范围进行必要验证。

在设计尚未确认前，不因这些目标而擅自扩大实现范围、重构无关系统或改变既有玩法规则。

# 当前开发方向

当前优先完成核心玩法系统并提高其可靠性；在保留现有可运行玩法的前提下做有针对性的改进，并加入模块化、可替换的战斗反馈占位效果。敌人攻击、受击、玩家受伤的当前效果仅用于建立接入点；未来可替换为专用动画、受击表现及血液效果，现阶段不视为正式素材。

存档系统开发暂缓，等待主要玩法功能足够完整后由用户明确决定恢复。无关任务不实现、重新启用、扩展或重构存档功能；保留现有遗留代码与用户修改。

`CardBuff` 的持续时间、剩余次数和可变状态应由单卡持有、整手共享或混合持有，仍未确定。当前行为保持原样；最终归属留待设计确认，明确缺陷仅做必要的最小修正。
