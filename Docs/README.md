# LW_game_development

# 项目概览

本文档是项目的快速入口，面向：

-   开发者；
-   Web GPT；
-   Desktop Codex；
-   其他参与项目开发的 AI 或人员。

它用于快速恢复项目上下文，包括：

-   项目是什么；
-   当前开发环境；
-   当前开发阶段；
-   当前主要目标；
-   当前阻塞问题；
-   下一步开发方向；
-   人与 AI 如何协作推进项目。

本文档描述的是**当前项目状态摘要**。

当需要确认实际实现时，应以：

-   真实工作区文件；
-   Godot Editor 状态；
-   Runtime 行为；

作为最终事实来源。

README 不替代：

-   `/AGENTS.md`
-   `Docs/GAME_DESIGN.md`
-   `Docs/ARCHITECTURE.md`
-   `Docs/CODEMAP.md`

------------------------------------------------------------------------

# 文档体系

本项目使用多个文档维护不同类型的信息。

  文件                     作用
  ------------------------ ----------------------------------------
  `/AGENTS.md`             AI 协作规则、修改原则、验证要求
  `Docs/README.md`         项目状态、当前阶段、开发方向、协作流程
  `Docs/GAME_DESIGN.md`    游戏设计目标、玩法规则、玩家体验
  `Docs/ARCHITECTURE.md`   系统关系、职责边界、接口、数据流
  `Docs/CODEMAP.md`        AI 实现阶段的代码导航和文件定位

------------------------------------------------------------------------

# AI 协作工作流

本项目采用：

    需求讨论与规划
            ↓
    生成实现任务
            ↓
    Codex 执行
            ↓
    验证与反馈

的双阶段 AI 协作模式。

目标：

当开启新的 Web GPT 对话、新模型会话，或者新的 Desktop Codex
工作环境时，只需要提供项目文档和当前任务，即可快速恢复一致的项目理解，并继续产生符合项目方向的实现。

------------------------------------------------------------------------

# 第一阶段：需求讨论与任务规划

## 使用对象

-   Web GPT
-   其他推理模型
-   开发者与 AI 的讨论过程

## 目标

这一阶段不是修改代码，而是：

-   理解需求；
-   明确目标；
-   分析影响范围；
-   确认实现方案；
-   生成明确的 Codex 任务。

## 规划阶段文档使用方式

### README

用于了解：

-   当前项目是什么；
-   当前开发阶段；
-   当前目标；
-   当前阻塞问题；
-   下一步方向。

### GAME_DESIGN

用于确认：

-   游戏应该如何工作；
-   玩家体验目标；
-   已确定设计；
-   未确定设计。

### ARCHITECTURE

用于确认：

-   系统之间的关系；
-   已存在职责边界；
-   数据流；
-   实现限制。

### CODEMAP

用于辅助确认：

-   可能涉及的代码区域；
-   当前实现入口；
-   相关文件位置。

规划阶段最终输出：

一份给 Desktop Codex 的实现任务说明。

任务说明应该包含：

-   目标；
-   期望行为；
-   影响范围；
-   实现限制；
-   可能修改的文件；
-   验证要求。

------------------------------------------------------------------------

# 第二阶段：Codex 实现与验证

## 使用对象

-   Desktop Codex

## 目标

根据明确任务，在真实项目环境中完成：

-   文件定位；
-   代码修改；
-   场景调整；
-   验证测试；
-   结果反馈。

## Codex 工作流程

    读取任务说明

            ↓

    README
    确认当前项目状态

            ↓

    CODEMAP
    定位实现文件

            ↓

    检查真实源码 / Scene / Resource

            ↓

    必要时阅读 ARCHITECTURE
    理解系统关系

            ↓

    必要时阅读 GAME_DESIGN
    确认玩法目标

            ↓

    进行最小范围修改

            ↓

    验证结果

            ↓

    反馈实际情况

CODEMAP 是实现阶段的主要导航入口。

文档用于提供上下文。

真实工作区、Godot Editor 和 Runtime 状态是最终实现事实。

------------------------------------------------------------------------

# 协作原则

## 用户负责

用户负责：

-   最终设计决策；
-   未确定需求确认；
-   项目方向控制；
-   实现结果验收。

AI 不应该替代用户决定：

-   未设计玩法；
-   未确认规则；
-   未确认架构变化。

## AI 负责

AI 负责：

-   理解已有信息；
-   发现不确定点；
-   提供实现方案；
-   执行明确任务；
-   验证实际结果。

目标不是替代开发者，而是让人和 AI 可以基于相同项目理解持续协作。

# 项目概况

`LW_game_development` 是一个以：

-   第一人称程序生成远征；
-   逻辑时间轴卡牌战斗；
-   "武器即牌组"构筑；

为核心方向的游戏项目。

------------------------------------------------------------------------

# 当前开发阶段

当前阶段目标：

完成远征系统最基础可运行闭环：

    地图生成
        ↓
    触发战斗
        ↓
    进行战斗
        ↓
    结束战斗
        ↓
    继续探索

当前重点：

验证一次完整远征流程中的：

World ↔ Battle

交互闭环。

------------------------------------------------------------------------

# 当前开发方向

当前优先级：

    1. 明确最低可运行 Battle 内容

            ↓

    2. 完成单次 Battle 生命周期

            ↓

    3. 完成 Battle → Expedition 返回

            ↓

    4. 恢复 World 探索状态

            ↓

    5. 验证连续探索与多次战斗

------------------------------------------------------------------------

# 工具链与验证

Godot CLI：

``` powershell
.\tools\godot_cli.ps1 <Godot args>
```

验证原则：

根据任务选择最小必要验证：

1.  源码检查；
2.  Godot CLI 验证；
3.  Scene 运行验证；
4.  Editor 状态验证；
5.  Runtime 行为验证。

不能仅通过静态代码分析声称运行行为正确。
