# LW_game_development


# 项目概览

本文档是项目的快速入口，面向：

- 开发者；
- Web GPT；
- Desktop Codex；
- 其他参与项目开发的 AI 或人员。

它用于快速恢复项目上下文，包括：

- 项目是什么；
- 当前开发环境；
- 当前开发阶段；
- 当前主要目标；
- 当前阻塞问题；
- 下一步开发方向；
- 人与 AI 如何协作推进项目。

本文档描述的是**当前项目状态摘要**。

当需要确认实际实现时，应以：

- 真实工作区文件；
- Godot Editor 状态；
- Runtime 行为；

作为最终事实来源。

# 项目概况

`LW_game_development` 是一个以：

- 第一人称程序生成远征；
- 逻辑时间轴卡牌战斗；
- "武器即牌组"构筑；

为核心方向的游戏项目。

# 当前开发阶段

项目当前在已有远征核心玩法的基础上，开始推进 **基地（Base）与远征（Expedition）之间的应用级流程**。

当前已接通 WeaponInstance 拥有的战斗/备用双牌组、最小保存和应用级场景流程。主菜单正常进入 Base；Base 复用完整 PlayerVisual 控制、碰撞和相机，按 P 通过 GameManager.start_expedition() 保存后进入远征。中断恢复武器与双牌组并直接生成新远征；死亡确认保存并清标记后返回 Base，胜利继续探索。尚无设施交互或整备 UI。

远征探索阶段按 L 可保存玩家武器与双牌组、清除中断标记并直接返回 Base；战斗、准备阶段、待确认结果与场景切换期间均拒绝。集中逻辑检查 31 项、0 失败，覆盖状态限制、重复输入、保存失败、正常返回、死亡返回和中断恢复。Base 与 Expedition 的控制脚本和配置相同；经主菜单进入的隔离运行中，落地相机高度约 1.650、步行速度 2.5、60 个物理帧前进约 2.250，两边一致。用户反馈的 Base 偏慢/偏低尚未复现，未调整控制参数；移动手感与视觉仍待人工检查。

WeaponData 使用 starting_combat_deck_card_ids / starting_reserve_deck_card_ids。已有 testweapon（3001）配置 20 张战斗牌（14 Attack、6 Skill）与 10 张备用牌（6 Attack、4 Skill）；Attack 1001–1005 各 4 张，Skill 2001–2002 各 5 张。Scripts/NewGame.tres 指定初始武器 3001，仅创建新玩家武器，不重置已有牌组。本轮集中隔离逻辑探针 72 项检查、0 失败，覆盖开门到正式 Battle、容器保存/恢复、P 入口、死亡/中断恢复和缺失内容；未做视觉、截图、导出或全面战斗回归。CLI 报告系统证书库读取错误，但未阻止本次逻辑验证。


## 既有远征核心目标

此前阶段的基础目标是完成远征系统最基础的可运行闭环：

```
地图生成

    ↓

触发战斗

    ↓

进行战斗

    ↓

结束战斗

    ↓

继续探索
```


既有核心流程仍以以下交互为基础：

```
World ↔ Battle
```

本阶段不替代或重写这条既有流程；后续改动应在需要时对受影响的远征流程进行回归验证。


## 当前阶段目标：基地与远征循环

`BaseSystem/Base.tscn` 保留 Field 与 Interactive items，并实例化已有完整 PlayerVisual.tscn。Base.gd 仅接收 P 动作并调用保存感知入口；无设施交互或牌组编辑 UI。角色移动手感与画面由用户手动验收。

当前阶段计划逐步实现以下目标：

1. **基地整备：** 玩家能够编辑武器及其绑定的牌组，延续项目“武器即牌组”的核心方向。
2. **进入远征：** 玩家能够从基地进入现有远征流程。
3. **返回基地：** 死亡确认后保存并返回 Base；另提供探索阶段的 L 主动返回入口，不增加损失或撤退惩罚。
4. **整备配置接入远征：** 基地中编辑的武器与牌组需要在进入远征后真正影响远征使用的玩家/战斗输入，而不能只停留在整备界面中。

预期的整体流程方向：

```
Base
  ↓
编辑武器及其绑定牌组
  ↓
进入 Expedition
  ↓
继续既有的 World ↔ Battle 流程
  ↓
玩家在远征中死亡
  ↓
返回 Base
```

以上内容是当前阶段目标摘要，不表示这些功能已经完成，也不提前决定具体实现方案。


## 实现前的设计讨论范围

开始编写实现任务前，将逐项讨论并确认需求，包括但不限于：

- 玩家如何在基地中移动、交互并打开整备功能；
- 基地的画面内容、整备界面与其他 UI 的布局和操作方式；
- 武器双牌组与战斗牌组最多 20 张已确认；牌组编辑交互与其余操作规则仍待确定；
- 基地进入远征时，整备配置如何交给现有远征系统并被实际使用；
- 玩家死亡、远征结束、返回基地时的流程与状态处理；
- 基地场景需要新增哪些模型、交互物件或其他场景节点，以及它们的外观和用途；
- 对应的代码职责、数据流、场景切换方式和验证要求。

上述细节目前均不应仅凭 README 推定为已确定设计。交互方式、UI 视觉、模型造型、节点结构、代码架构与具体数据结构，都应在后续讨论中确认后再形成 Codex 实现任务。


## 当前阶段推进顺序

1. 更新 README，记录当前进度、目标与未决设计。
2. 逐项讨论并确认玩法交互、UI/画面、场景模型、数据流和代码实现边界。
3. 形成范围明确的英文 Codex 任务说明。
4. 按确认后的方案增量实现，并按任务范围进行必要验证。

在设计尚未确认前，不因这些目标而擅自扩大实现范围、重构无关系统或改变既有玩法规则。

# 当前开发方向

当前优先完成核心玩法系统并提高其可靠性；在保留现有可运行玩法的前提下做有针对性的改进，并加入模块化、可替换的战斗反馈占位效果。敌人攻击、受击、玩家受伤的当前效果仅用于建立接入点；未来可替换为专用动画、受击表现及血液效果，现阶段不视为正式素材。

当前最小存档保存拥有的 WeaponInstance、当前武器 UID、各自的 combat_deck / reserve_deck 及 expedition_was_active；没有独立玩家卡牌仓库。进入远征前、死亡确认后与探索 L 主动返回时保存；中断恢复生成新远征，不恢复旧地图/房间/战斗。Room Entry / Battle Start checkpoint、战斗快照和其他存档扩展继续暂缓，旧 BattleSaveModule 未启用。

`CardBuff` 的持续时间、剩余次数和可变状态应由单卡持有、整手共享或混合持有，仍未确定。当前行为保持原样；最终归属留待设计确认，明确缺陷仅做必要的最小修正。
