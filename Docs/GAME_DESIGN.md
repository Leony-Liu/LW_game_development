# 一、游戏定位

## 1. 核心定位【试玩版已确定】

这是一款以**第一人称程序生成远征 + 行动轴卡牌战斗 + 高风险武器构筑**为核心的游戏。

试玩版体验由以下要素组成：

- 随机地图探索；
- 搜集、战斗、存放、撤离的风险循环；
- 以逻辑行动轴为核心、而非传统轮流回合制的卡牌战斗；
- “武器就是牌组”的长期构筑；
- 提灯燃料、生命值和携带重量共同形成的远征压力；
- 魂同时承担局内强化与长期成长资源；
- 玩家始终可以选择提早撤离，但深入地图、完成任务、挑战精英和 Boss 能获得更高收益。

玩家带着一把已经构筑的武器进入程序生成地图，在有限资源压力下不断做选择：

```text
继续深入
vs
返回初始房存放
vs
立即撤离
```

成功撤离才真正兑现本次远征收益；死亡则失去本次远征资源，并失去带入远征的武器与其完整牌组。

---

## 2. 核心体验支柱【试玩版已确定】

### 2.1 风险决策

玩家不被强制要求清完整张地图。

任何时候都可以撤离，但越深入，越可能获得：

- 更多魂；
- 更多物资；
- 更好的局内构筑机会；
- 任务链奖励；
- 精英奖励；
- Boss 奖励。

游戏应持续给玩家一个明确问题：

> “我现在已经拿到的东西，值不值得为了更高收益继续冒险？”

### 2.2 有限灯火

提灯燃料是探索阶段的时间预算。

它不是传统关卡倒计时，而是让玩家意识到：

- 继续探索需要付出时间；
- 返回初始房也需要时间；
- 某些远距离收益必须计算“去程 + 回程”；
- 补充燃料能改变一次远征的可探索范围。

### 2.3 携带压力

物资采用重量制携带。

有限承重迫使玩家在远征中反复：

```text
搜刮
→ 装满
→ 返回初始房
→ 存放
→ 再次出发
```

目标不是制造复杂背包整理，而是形成路线与风险决策。

### 2.4 持续损耗

一次远征共享同一份生命值状态。

战斗结束不会自动回满生命值，因此每一场战斗都会影响之后的探索决策。

### 2.5 局内构筑

敌人提供魂，魂可以在卡牌工作台转换为当前武器牌组的即时成长。

玩家会不断在：

```text
现在把魂投入本局构筑
vs
继续保留魂
vs
带着魂撤离用于长期成长
```

之间取舍。

### 2.6 高风险长期资产

武器就是牌组。

一把长期培养的武器被带进远征后，同时是一项高价值风险资产。死亡会让武器和整套牌组一起丢失。

### 2.7 开门的不确定性

普通门不提前泄露下一房间的普通风险与奖励。

玩家在状态较差时也可能打开一扇门后遇到危险。

Boss 门必须明显不同，确保玩家不会在非主动决策下误入试玩版最高级别挑战。

# 二、完整游戏愿景与试玩版边界

## 3. 正式版长期循环【正式版】

长期目标：

```text
3D 基地
→ 整备
→ 地图准备
→ 远征
→ 搜刮 / 战斗 / 局内构筑
→ 深层目标
→ 撤离
→ 长期成长
→ 再次出征
```

正式版愿景包括：

- 可自由移动、具备归属感的真实 3D 基地；
- 近战与远程两大武器类别；
- 近战进一步分为短、中、长三类；
- 更多武器、卡池、装备与局内道具；
- 完整装备系统；
- 武器 / 牌组保险或其他风险缓解系统；
- 正式的提灯升级路线；
- 更丰富的商店和免费武器池；
- 更复杂的地图生成干预；
- 更完整的长期成长、阶段解锁和经济循环。

---

## 4. 试玩版基地【试玩版已确定】

试玩版基地采用**界面式基地**，不制作可自由移动的 3D 基地空间。

至少包含：

### 4.1 商店

- 每次远征结束后刷新 3 个免费武器选项；
- 玩家可以消耗魂重新刷新；
- 可以消耗魂购买局内道具，例如治疗道具；
- 免费武器机制用于避免玩家因连续失去武器而陷入软锁。

试玩版内容量有限，因此免费武器池的多样性可以低于正式版，但机制保留。

### 4.2 工作台

基地工作台可以：

- 管理武器和牌组；
- 升级武器；
- 升级已有卡牌；
- 删除卡牌；
- 升级斧头；
- 显示装备系统占位；
- 显示提灯升级占位。

试玩版中提灯基础时长固定，不完成正式升级路线。

### 4.3 角色界面

可以：

- 管理当前武器；
- 管理局内道具；
- 查看装备槽位占位；
- 消耗魂提升角色基础最大生命值。

### 4.4 远征准备

开始远征前可以：

- 选择本次武器 / 牌组；
- 携带允许带入的局内道具；
- 决定携带多少已有魂；
- 调整允许的地图生成倾向；
- 开始远征。

地图生成干预的具体项目与成本属于【数值待调 / 制作目标】，但其设计方向是：

> 玩家可以付出资源或承担更高风险，主动改变地图的奖励与危险倾向。

---

## 5. 试玩版武器范围【制作目标】

试玩版聚焦：

```text
近战
→ 中长度
```

当前内容目标：

- 3 把完整可玩的中长度近战武器；
- 第 4 把仅在进度充足时制作；
- 不做远程武器；
- 不完整制作短武器和长武器类别。

以上是当前试玩版内容目标。用户可以根据实际制作条件显式调整内容数量，但不应因此破坏本文确认的核心玩法结构。

---

# 三、远征核心循环

## 6. 单次远征循环【试玩版已确定】

```text
基地准备
→ 远征准备
→ 进入初始房
→ 探索地图
→ 搜刮 / 战斗 / 使用设施
→ 获得物资和魂
→ 返回初始房存放
→ 决定再次深入或撤离
→ 成功撤离
→ 结算长期资源
→ 返回基地
```

任务链和 Boss 都是可选的深层目标，不会自动结束远征。

---

## 7. 单次远征目标时长【试玩版已确定】

标准成功远征的目标现实游玩时间约为：

```text
20 分钟
```

这不是硬性倒计时。

初始燃料提供约 10 分钟的**可消耗探索时间**，但以下阶段会暂停燃料：

- 战斗；
- 卡牌工作台交互。

因此实际现实游玩时间会自然长于剩余燃料时间。

允许：

- 早期撤离明显短于 20 分钟；
- 深入探索、任务链、Boss 与额外燃料使远征超过 20 分钟。

---

# 四、提灯与远征压力

## 8. 提灯与燃料【试玩版已确定】

提灯同时承担：

- 黑暗环境中的照明；
- 探索时间压力。

基础规则：

- 初始燃料：10 分钟；
- 探索时持续消耗；
- 初始房内持续消耗；
- 普通移动与搜刮期间持续消耗；
- Battle 期间世界暂停，燃料暂停；
- 卡牌工作台交互期间燃料暂停；
- 初始房不会补充、重置或暂停燃料；
- 补充燃料直接增加剩余时间，不占背包格；
- 燃料耗尽后进入致命危险，并最终导致死亡。

### 8.1 燃料来源

试玩版：

- 小油瓶：+3 分钟，可从物资箱获得；
- 大油瓶：+5 分钟，可作为房间开放内容出现；
- 燃料补充站：+10 分钟，占据房间中央设施位。

### 8.2 待调整内容【数值待调】

- 最大燃料是否存在上限；
- 燃料来源出现概率；
- 补充站具体使用条件；
- 燃料耗尽后的致命过程、警告和缓冲时间。

---

## 9. 三种核心远征压力【试玩版已确定】

玩家在探索中同时管理：

### Fuel

限制还能够探索多久，以及能否安全返回初始房。

### Carry Weight

限制还能带走多少具体物资，推动玩家返回存放。

### HP

记录跨战斗的持续损耗，影响玩家是否还能承担下一次战斗。

三者共同形成：

```text
时间压力
+
空间 / 物流压力
+
生存压力
```

# 五、资源、携带与经济

## 10. 局内资源类别【试玩版已确定】

远征主要产生两类高层收益：

### 10.1 具体物资

来源主要是环境探索，例如：

- 破坏物资箱；
- 拾取房间内物件；
- 任务奖励。

地图中出现的是具体物件，例如：

- 机箱；
- 鼠标；
- 键盘。

每种具体物资需要通过数据配置定义：

- 编号；
- 显示名称；
- 重量；
- 木材转换量；
- 金属转换量；
- 塑料转换量；
- 掉落权重；
- 来源。

具体清单和转换数值不写死在核心玩法代码中。【数值待调】

### 10.2 魂

主要通过击败敌人获得。

魂同时是：

- 当前远征的构筑资源；
- 当前远征的医疗资源；
- 可携带的风险资产；
- 长期成长货币。

玩家允许从基地携带已有魂进入远征。

---

## 11. 重量制携带【试玩版已确定】

物资使用重量制，不使用格子拼图式背包。

随身容量有限。

需要明确区分：

```text
随身携带
远征仓库
基地长期资源
```

### 随身携带

当前角色身上的具体物资与魂。

受到随身承重限制。

### 远征仓库

位于初始房。

不受随身重量限制，但仍然只属于本次远征。

### 基地长期资源

只有成功撤离后才进入长期存档。

---

## 12. 基地长期资源【试玩版已确定】

基地持有四类核心资源：

```text
木材
金属
塑料
魂
```

### 12.1 物资结算

成功撤离时：

```text
具体物资
→ 木材 / 金属 / 塑料
```

具体转换按物资数据定义。

### 12.2 木材 / 金属 / 塑料用途

主要用于：

- 武器升级；
- 卡牌升级；
- 治疗道具制作；
- 正式版更多制作和升级。

### 12.3 魂用途

远征内：

- 卡牌工作台抽取新卡；
- 复制卡牌；
- 医疗设施制作治疗道具；
- 未来其他局内服务。

基地：

- 新武器或阶段解锁；
- 商店刷新；
- 商店购买治疗道具；
- 提升角色基础最大生命值；
- 未来其他长期成长。

# 六、初始房、存放、撤离与死亡

## 13. 初始房【试玩版已确定】

初始房是一个真实存在于地图中的房间。

它是：

- 本次远征的物流中心；
- 资源存放点；
- 撤离点。

它不是：

- 安全暂停菜单；
- 免费恢复点；
- 燃料补给点。

停留在初始房期间仍消耗燃料。

---

## 14. 资源存放设施【试玩版已确定】

玩家靠近后执行普通交互，例如按 `E`：

```text
随身魂
+
随身具体物资
→ 全部转入远征仓库
```

规则：

- 一次交互全部存放；
- 不打开复杂库存管理界面；
- 存放完成后可以立即继续探索；
- 存放不等于保险；
- 玩家之后如果死亡，远征仓库仍全部丢失。

---

## 15. 撤离设施【试玩版已确定】

玩家可以在任何时候返回初始房并主动撤离。

撤离流程：

```text
交互
→ 撤离表现
→ 结束当前远征
→ 结算远征仓库
→ 具体物资转换
→ 长期资源入账
→ 返回基地
```

深入目标不会替代撤离。

即使击败 Boss，也仍需要安全返回并成功撤离才能兑现奖励。

---

## 16. 死亡与主动放弃【试玩版已确定】

死亡时：

- 清空当前随身资源；
- 清空远征仓库；
- 失去带入远征的武器；
- 失去该武器完整构筑牌组；
- 试玩版不提供保险。

玩家主动选择放弃 / 退出当前远征时：

```text
按死亡处理
```

斧头属于永久工具，不因远征死亡丢失。

---

# 七、地图与房间

## 17. 地图规模【试玩版已确定 / 数据驱动】

试玩版标准目标：

```text
30 ± 5 个房间
```

必须通过：

- `MapBlueprint`；
- 远征测试配置；
- 其他数据资源；

进行调整。

不得把目标房间数、内容概率或奖励概率写死在核心生成逻辑里。

以下均属于【数值待调】：

- 普通房内容比例；
- 物资房比例；
- 任务房生成；
- 精英分布；
- 工作台概率；
- 医疗设施概率；
- 燃料设施概率；
- Boss 相关配置。

---

## 18. 门与房间未知性【试玩版已确定】

### 普通门

- 普通门外观一致；
- 玩家不能仅根据普通门判断下一房间具体内容；
- 开门应具备“抽奖 / 冒险”的心理效果；
- 当前状态较弱时也可能开到高风险房间。

### Boss 门

- 外观明显不同；
- 明确告诉玩家这是最高风险目标；
- 玩家必须主动决定是否进入。

---

## 19. 标准房间逻辑布局【试玩版已确定】

每个标准正方形房间具有：

### 4 个门生成位

位于：

```text
北 / 东 / 南 / 西
```

### 4 个进入方向恢复点

对应玩家从：

```text
北 / 东 / 南 / 西
```

进入房间后的恢复位置。

这些恢复点服务于房间入口 checkpoint。

### 5 个内容刷新位置

```text
左上
右上
左下
右下
中央
```

设施只允许生成在中央内容位。

---

## 20. 普通房组合规则【试玩版已确定】

普通房不使用互斥的“敌人房 / 工作台房 / 箱子房”结构。

同一个普通房可以组合：

- 敌人；
- 物资箱；
- 卡牌工作台；
- 露天燃料；
- 其他允许共存的内容。

具体组合与概率通过数据配置调整。

---

## 21. 物资房【试玩版已确定】

物资房是纯奖励房。

规则：

- 必定没有敌人；
- 必定没有卡牌工作台；
- 必定没有医疗设施；
- 必定没有燃料补充站；
- 五个内容位置全部生成物资箱；
- 每个位置 3 个；
- 总计 15 个物资箱。

---

## 22. 物资箱与斧头【试玩版已确定】

试玩版只制作一种物资箱。

默认：

- 斧头攻击 3 次破坏；
- 物资在箱子被破坏时随机决定；
- 允许读档重新随机；
- 不开发防读档刷箱子系统。

斧头：

- 属于永久 Tool；
- 不随死亡丢失；
- 有长期升级路线；
- 最终可升级到 1 次攻击破箱。

具体升级成本属于【数值待调】。

---

# 八、深层目标

## 23. A → B → C 任务链【试玩版已确定】

地图可以生成一条独立深层任务链：

```text
任务房 A
→ 获得任务物品
→ 携带至任务房 B
→ B 解锁 / 显示任务房 C
→ 前往 C
→ 完成任务并获得高价值奖励
```

任务奖励可以包含：

- 大量魂；
- 大量物资；
- 高价值物资；
- 一次燃料补充。

任务链的核心设计作用：

> 在玩家剩余燃料不足时制造“现在撤离还是继续赌更高收益”的明确决策。

任务链与 Boss 互相独立，可以在同一次远征同时存在。

---

## 24. Boss【试玩版已确定】

Boss 是可主动选择的最高级挑战之一。

作用：

- 验证当前构筑是否已经成型；
- 提供显著高于普通遭遇的战斗挑战；
- 提供大量奖励。

Boss 胜利：

```text
不会直接结束远征
```

玩家必须之后返回初始房并成功撤离。

---

# 九、战斗核心设计

## 25. 战斗定位【试玩版已确定】

战斗不是传统：

```text
玩家回合
→ 敌人回合
→ 玩家回合
```

而是围绕：

```text
逻辑行动轴
```

组织。

战斗中的时间是玩法资源。

玩家打出的牌不仅产生效果，也推动逻辑时间，使敌人行动、资源恢复和其他时间相关机制发生。

---

## 26. 战斗启动输入【试玩版已确定】

一场战斗需要的高层输入：

- 战斗开始时的玩家数据；
- 当前武器对应的牌组；
- 当前敌人编号。

战斗结束后：

- 回到同一次远征；
- 回到同一张地图；
- 回到同一个房间上下文；
- 保留远征层生命值、燃料、资源与任务状态。

具体类名、方法签名和 signal 属于 `Docs/ARCHITECTURE.md` / `Docs/CODEMAP.md`，不在本文件作为设计权威维护。

---

## 27. 世界与战斗的暂停关系【试玩版已确定】

Battle 期间：

- 世界探索暂停；
- 玩家探索移动与交互不继续运行；
- 提灯燃料暂停；
- 战斗使用自己的逻辑时间。

动画现实耗时不应改变行动轴的逻辑时间。

---

## 28. 远征生命值【试玩版已确定】

一次远征共享持续生命值。

规则：

- 战斗受到的生命损失会保留；
- 战斗胜利不自动回满；
- 下一场战斗继承当前生命值；
- 医疗设施和治疗道具负责恢复；
- 生命值与 Fuel、Carry Weight 共同形成远征压力。

---

## 29. 体力与法力【试玩版已确定】

体力和法力是战斗内部资源。

二者的恢复都与**逻辑行动轴时间**关联，而不是现实秒数。

基本结算顺序：

```text
玩家使用卡牌
→ 支付该卡牌对应资源
→ 卡牌推动逻辑时间
→ Timeline 推进
→ 根据推进的逻辑时间结算体力 / 法力恢复
```

示例：

如果某资源设计为：

```text
每 20 logical time 恢复 1
```

那么一张推进 20 logical time 的卡，在支付成本后，随着本次时间推进恢复 1 点对应资源。

### 29.1 数值与资源映射【数值待调 / 待设计】

尚未锁定：

- 最大体力；
- 最大法力；
- 各自回复速度；
- 回复是否允许超过最大值：预期不应超过最终定义的最大值，但精确属性模型需随战斗设计确认；
- `Attack / Skill / Power` 最终各自使用 stamina 还是 mana；
- 是否存在不消耗两者之一的特殊卡牌。

在这些规则正式确定前，不应仅根据旧代码行为推导最终设计。

---

## 30. 逻辑时间与现实表现分离【试玩版已确定】

```text
logical time ≠ animation duration
```

一张牌推进多少逻辑时间，由玩法数据决定。

动画播放时间只负责表现。

如果 Timeline 等待表现结束，也不能因此让现实动画长度改变卡牌的逻辑 `time_cost`。

---

## 31. 行动时序【部分待设计】

确定原则：

- 每个行动具有发生的逻辑时间；
- 玩家卡牌的时间成本会推动 Timeline；
- 敌人行动同样进入统一行动轴；
- 玩家与敌人的主要战斗行为应在同一个时序模型下结算。

尚未正式锁定的细节【待设计】：

- 同 `trigger_time`、同优先级时最终采用什么 tie-break；
- `priority == 0` 是否永久代表“立即触发但仍消耗时间”；
- 是否需要独立的 instant / cast timing 字段；
- priority 的最终设计语义及允许范围。

当前实现行为不能自动成为上述问题的最终设计答案。

---

## 32. 统一战斗行动【设计原则】

玩家卡牌与敌人行动应尽量进入同一套行动表达模型，而不是分别拥有彼此不兼容的结算协议。

设计目标：

```text
玩家卡牌
或
敌人行动
→ 统一行动
→ Timeline 排期
→ 实体 / 卡牌状态结算
```

具体 `CombatAction` 字段、调用路径和 owner 属于架构文档；这里保留的是玩法设计原则：

> 新战斗效果应优先考虑是否能进入统一行动模型，避免再造平行的战斗规则。

---

## 33. 伤害与防御【部分待设计】

试玩版确定需要：

- 直接伤害；
- 生命值；
- 能够表达基础防护 / shield 类效果的空间。

尚未正式决定【待设计】：

- defense / armor 公式；
- critical hit；
- accuracy / evasion；
- elemental resistance；
- shield 是否随时间衰减；
- shield 是否在战斗结束后清空；
- shield 是否有上限；
- 是否存在绕过 shield 的伤害类型。

未确认的扩展机制不能仅因为旧代码中出现相关字段就默认进入最终设计。

---

## 34. 增益 / Buff 设计【部分待设计】

卡牌和战斗系统允许存在：

- 对卡牌数值的临时修改；
- 对实体属性的临时修改；
- 按逻辑时间或行动次数消耗的效果。

设计上仍需继续确定【待设计】：

- 同类型 `SET / ADD / MULTIPLY` 修改的稳定顺序；
- 多个同类型 Buff 的结算顺序；
- Buff 的次数消耗发生在 request、confirm、action trigger、action resolve 中的哪一步；
- 时间持续型 Buff 的精确 tick 规则；
- 战斗结束时哪些 Buff 必须清空；
- 哪些长期卡牌 modifier 会转化为战斗内 Buff。

实现必须避免同一效果被两个独立结算路径重复应用。

---

# 十、敌人设计

## 35. 试玩版敌人层级【试玩版已确定】

试玩版至少包含：

### 普通敌人 × 2

作用：

- 低风险获取魂；
- 让玩家理解基础战斗；
- 提供至少两种不同的基础行为模式。

### 精英 × 1

作用：

- 面向已经有一定构筑的玩家；
- 提供更高风险；
- 提供明显更高的魂收益。

### Boss × 1

作用：

- 验证成型构筑；
- 提供最高等级战斗挑战；
- 提供高价值奖励。

---

## 36. 敌人行动轴行为【试玩版已确定】

敌人应在逻辑 Timeline 中持续规划并行动，而不是只在战斗开始时安排一次行动后停止。

敌人可以具有：

- 不同行动；
- 行动时间成本；
- cooldown；
- 权重；
- 效果数据。

具体 AI 选择算法可以采用数据驱动和加权随机。

“由哪个 manager / signal 触发下一次 AI planning”属于架构问题，由 `Docs/ARCHITECTURE.md` 决定；本文件只要求玩家层面的结果：

> 只要战斗仍在进行，敌人行动规划能够持续形成完整闭环。

---

# 十一、武器、牌组与卡牌

## 37. 武器就是牌组【试玩版已确定】

武器不是独立装备 + 一个外部牌组。

武器本身就是牌组的长期载体。

一把武器至少承载：

- 初始牌组；
- 远征中获得的新卡；
- 已有卡牌的升级状态；
- 删除 / 复制后的牌组结构；
- 武器升级对一部分卡牌的影响。

死亡失去武器：

```text
= 失去整个构筑牌组
```

---

## 38. 武器升级作用范围【试玩版已确定】

武器升级不要求无条件影响所有牌。

可以按：

- 卡牌标签；
- 功能类别；
- 攻击类别；
- 武器专属关系；

影响一部分卡。

例如：

> 砍刀升级可以提高普通攻击牌伤害，但不提高“让下一次攻击 +50%”的纯增幅牌。

具体标签体系与数据结构由后续实现设计。

---

## 39. 新卡获取【试玩版已确定】

新的卡牌只能在远征中获得。

基地可以：

- 升级武器；
- 升级已有卡牌；
- 删除卡牌；
- 管理牌组。

基地不能直接生成新的卡牌。

---

## 40. 卡池结构【试玩版已确定】

试玩版武器属于中长度近战。

每把武器的可获取卡池：

```text
中长度近战公共卡池
+
当前武器专属卡池
```

当前内容方向：

- 单武器专属：约 5–8 张专属行动牌；
- 单武器专属：约 3–5 张专属技能牌；
- 中长度近战公共：约 20–30 张公共行动牌；
- 中长度近战公共：约 15–20 张公共技能牌。

这些是内容设计范围，不是硬性代码常量。

最终实际卡牌数量由制作进度控制。【制作目标】

---

## 41. 卡牌功能角色【试玩版已确定】

卡牌设计围绕一次攻击过程中的功能角色：

```text
启动
→ 增幅
→ 输出
→ 终结
```

这些是**设计角色**，不是强制 `CardType`。

一张牌可以承担多个角色。

一个环节也可以由：

- 卡牌；
- 局内道具；
- Buff；
- 武器机制；

承担。

### 41.1 小套装设计

卡牌内容优先采用“机制小套装”生产。

例如三张牌：

```text
第一张：启动
第二张：增幅
第三张：输出 + 终结
```

如果按正确顺序完成：

- 最后一击伤害翻倍；
- 或获得其他特殊效果。

这样允许一套机制衍生 5–8 张牌，而不要求每一张牌都拥有完全独立的复杂系统。

---

## 42. Card 类型与功能角色的关系【待设计】

当前战斗数据中存在类似：

```text
Attack
Skill
Power
```

的分类概念。

这些分类不等同于：

```text
启动
增幅
输出
终结
```

前者更接近卡牌数据 / 资源 / 战斗规则分类，后者是内容设计角色。

仍需确定：

- `Attack / Skill / Power` 的最终定义；
- 每一类默认支付哪种资源；
- 是否所有正式内容都需要保留 Power 分类；
- 是否需要额外标签系统表达“普通攻击”“增幅”“终结”等设计语义。

---

## 43. 卡牌三层生命周期设计【已确认原则】

卡牌在游戏中存在不同生命周期，不应把所有状态塞进同一种对象。

设计语义：

```text
静态卡牌模板
→ 一张可持久化的具体卡
→ 单场战斗内的临时卡牌状态
```

对应现有技术命名：

```text
CardData
→ CardInstance
→ RuntimeCard
```

这是有意的生命周期分层，不是计划合并的冗余结构。

### 43.1 静态模板

描述可复用的卡牌基础数据。

### 43.2 具体卡牌实例

属于武器 / 牌组的长期或远征级卡牌实例，可以承载升级、modifier 和 identity。

### 43.3 战斗内实例

只属于当前战斗，可以拥有临时 Buff 和计算后的战斗状态。

### 43.4 仍待确定【待设计】

- `CardInstance.unique_id` 是否必须进入 battle runtime；
- `CardInstance.modifiers` 如何转换为战斗内 modifier / Buff；
- 哪些 modifier 跨远征永久保留；
- 哪些效果只存在于当前 Battle。

---

# 十二、卡牌工作台

## 44. 工作台交互【试玩版已确定】

卡牌工作台是远征内构筑核心设施。

交互期间：

```text
Fuel 暂停
```

---

## 45. 抽卡【试玩版已确定】

流程：

```text
支付魂
→ 出现 3 张候选卡
→ 选择 1 张
→ 立即加入当前武器牌组
→ 后续战斗立即可使用
```

具体魂费用属于【数值待调】。

---

## 46. 权重规则【试玩版已确定】

候选概率受到：

- 当前武器；
- 中长度近战公共池；
- 当前武器专属池；
- 当前牌组已有卡牌数量；

影响。

原则：

> 同名卡当前拥有越多，再次出现的权重越低；未拥有或数量较少的卡相对更容易出现。

具体权重函数属于【数值待调】。

---

## 47. 复制与删除【试玩版已确定】

卡牌工作台提供：

### 复制

- 支付魂；
- 复制当前牌组中的一张卡。

### 删除

- 删除当前牌组中的一张卡；
- 返还一定魂。

具体费用和返还比例属于【数值待调】。

---

## 48. 工作台读档策略【试玩版已确定】

试玩版不制作防读档刷三选一结果系统。

允许玩家通过读取 checkpoint 重新获得不同候选结果。

# 十三、医疗与治疗

## 49. 远征生命恢复【试玩版已确定】

由于 HP 跨战斗继承，医疗是远征资源决策的一部分。

---

## 50. 医疗设施【试玩版已确定】

医疗设施可以：

- 消耗魂制作治疗道具；
- 随机提供一个免费治疗道具；
- 或没有免费内容。

免费内容可以在地图生成 / 房间状态建立时决定，使房间恢复时回到一致的进入状态。

具体免费概率属于【数值待调】。

---

## 51. 治疗道具【试玩版已确定】

试玩版至少包含：

```text
小型血针
中型血针
大型血针
```

基地也可以：

- 使用木材 / 金属 / 塑料制作；
- 在商店消耗魂购买。

治疗量、成本、制作配方属于【数值待调】。

---

# 十四、存档、Checkpoint 与恢复

## 52. 存档设计原则【试玩版已确定】

存档目标不是精确记录任何一帧 runtime 状态。

目标是：

> 以少量清晰 checkpoint 支持程序关闭、断电和继续游戏，同时控制实现复杂度。

试玩版主要使用两种恢复边界：

```text
Room Entry Checkpoint
Battle Start Checkpoint
```

---

## 53. 房间入口 Checkpoint【试玩版已确定】

每次玩家通过门进入一个新房间：

```text
创建 / 更新当前远征 checkpoint
```

checkpoint 表示：

> “刚刚进入这个房间的那一刻。”

恢复时玩家出现在对应进入方向的恢复点。

至少需要恢复到该时刻的：

- 当前 HP；
- 当前 Fuel；
- 当前武器 / 牌组；
- 随身资源；
- 远征仓库；
- 当前魂；
- 任务状态；
- 已经提交的地图 / 房间状态；
- 进入当前房间前已经完成的远征变化；
- 对应的 N / E / S / W 进入方向位置。

当前房间内尚未通过下一次门转换提交的操作，应全部回滚。

### 53.1 示例

玩家：

```text
90 HP
→ 进入房间
→ 使用免费血针
→ 100 HP
→ 打开几个物资箱
→ 程序关闭
```

重新加载：

```text
回到对应 RoomEntryAnchor
HP = 90
免费血针恢复
箱子恢复
当前房间回到进门时状态
```

当玩家进入下一房间时：

> 上一房间结果才进入新的 checkpoint，成为已经提交的历史状态。

---

## 54. 战斗开始 Checkpoint【试玩版已确定】

Battle 开始时记录：

- Battle 开始时玩家数据；
- Battle 开始时武器 / 牌组；
- enemy id。

如果 Battle 期间程序中断：

```text
重新加载
→ 从头开始整场 Battle
```

试玩版明确**不保存 Battle 中途状态**。

不序列化：

- `Timeline.current_time`；
- 当前 action queue；
- 战斗中途 HP；
- 战斗临时 Buff；
- draw / hand / discard 当前顺序；
- Enemy AI 中间 planning / cooldown 状态；
- animation / visual wait 状态。

因此旧设计中“精确恢复 Battle mid-state”不再是试玩版待决定项。

---

## 55. 读档刷结果策略【试玩版已确定】

试玩版不开发 anti-save-scumming。

允许：

- 物资箱破坏后通过重新加载改变即时掉落；
- 卡牌工作台重新加载后改变三选一结果。

不要为了阻止这种行为增加：

- RNG 锁定系统；
- 每次随机结果额外持久化；
- 复杂防作弊 checkpoint 数据。

如果未来为了技术上的确定性使用 seed，不应改变上述玩家体验原则。

# 十五、表现与交互原则

## 56. 逻辑优先、表现跟随【试玩版已确定】

主玩法逻辑优先跑通。

表现层通过：

- signal；
- event；
- command；
- presentation request；

接入玩法状态。

原则：

> 表现层可以反映 gameplay state，但不应成为 gameplay truth owner。

具体 signal 和 owner 由 `Docs/ARCHITECTURE.md` 定义。

## 57. 试玩版必须清晰反馈的状态【试玩版已确定】

- 当前 HP；
- 当前 Fuel；
- 低 Fuel 警告；
- 当前携带重量；

- 成功撤离结算。

---

## 58. 新玩家引导【制作目标】

第一次接触游戏的玩家应能理解：

1. 武器就是牌组；
2. Fuel 限制探索时间；
3. Battle 和卡牌工作台暂停 Fuel；
4. 物资按重量携带；
5. 初始房 Deposit 不是永久保险；
6. 只有成功撤离才真正兑现资源；
7. 死亡会失去武器和完整牌组；
8. 魂既可用于本局构筑，也可用于长期成长；
9. 可以随时撤离，但深层任务、精英和 Boss 奖励更高。

优先使用：

- UI；
- 第一局提示；
- 场景交互；
- 简短 contextual prompt；

完成引导。

试玩版不制作冗长独立教学关。

# 二十、试玩版设计完成标准

## 70. 核心体验验收

试玩版设计目标完成时，玩家应能够：

- 从基地完成整备并进入远征；
- 在程序生成地图中正常探索；
- 感受到 Fuel / HP / Carry Weight 三种压力；
- 搜刮具体物资；
- 使用斧头破坏物资箱；
- 战斗并获得魂；
- 使用卡牌工作台强化当前牌组；
- 使用医疗系统处理持续 HP 损耗；
- 返回初始房存放资源；
- 继续深入或主动撤离；
- 完成 A → B → C 任务链；
- 挑战精英；
- 主动挑战 Boss；
- 成功撤离并结算长期资源；
- 在死亡后正确失去风险资产；
- 在程序中断后从 Room Entry / Battle Start checkpoint 恢复；
- 理解“武器就是牌组”以及魂的双重用途。

# 二十一、维护规则

## 72. 什么时候更新 GAME_DESIGN

应更新本文，当：

- 用户确认新的 gameplay rule；
- 已有玩法规则发生改变；
- Demo / Full Game scope 改变；
- 一个【待设计】问题被正式决定；
- resource / reward / risk 的语义改变；
- battle timing / resource / Buff 等玩法语义改变；
- map / room / encounter / mission / extraction 规则改变；
- save / checkpoint 的玩家体验语义改变；
- Weapon / Deck / Card progression 规则改变。

---

## 73. 通常不因为这些事情更新

通常不要因为以下内容修改 GAME_DESIGN：

- 私有函数重构；
- 文件移动；
- SceneTree 接线变化；
- signal 名称变化但玩法不变；
- 某个实现 bug 修复但设计不变；
- AI collaboration workflow 改动；
- 当前 milestone 改变；
- 单纯实现进度变化。

这些分别属于真实实现或以下规范文档：

- `Docs/ARCHITECTURE.md`
- `Docs/CODEMAP.md`
- `Docs/README.md`

---

## 74. 设计文档使用规则

当用户、Web GPT 或 Desktop Codex 遇到玩法歧义：

```text
1. 先查本文件对应设计章节
2. 已明确 → 按设计实现
3. 【数值待调】 → 保持数据驱动，不自行锁死最终数值
4. 【待设计】 → 不擅自决定，向用户 / Web GPT 提出问题
5. 若真实代码与本文件冲突 → 报告 implementation gap
6. 不因为旧代码当前行为而自动改变本文件
```

如果本次任务本身获得了用户新的明确玩法决定，并且该决定改变了本文件内容，则应同步更新对应章节。

# 结语

本文件的核心目的不是记录“当前代码有哪些字段”，而是回答：

> **这个游戏应该怎样玩？**

当代码、旧机制文档、临时测试数据与已确认设计不一致时：

```text
不要猜
不要让旧实现替用户做设计决定
不要把临时数值升级为最终规则
```

先以本文件确认设计，再由 `ARCHITECTURE`、`CODEMAP` 和真实仓库决定应该如何实现。
