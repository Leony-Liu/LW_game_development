# Godot Project Code Architecture & Generation Standards

**Document:** `CODE_STANDARDS.md`\
**Version:** 1.0\
**Status:** Accepted — project-owner decision, 2026-11-03\
**Applies to:** GDScript, scenes, Resources, runtime data models, content-authoring tools, and AI-generated code.

------------------------------------------------------------------------

**Revision note:** This v1.0 revision clarifies the recursive System / Subsystem structure, the mandatory Entry + Manager pair, and Manager-led internal Component collaboration. Version 1.0 was formally accepted by the project owner on 2026-11-03.

## 0. Purpose, Scope, and Authority

### 0.1 Purpose

This document defines how code and data must be organized, connected, authored, and validated in this Godot project.

The project is organized around **systems and recursively nested subsystems**. Every formal System and Subsystem has exactly one Entry script and one Manager script. The Entry defines the boundary; the Manager coordinates internal work. Components may collaborate directly within explicit limits. Data contracts and mutable-state ownership remain explicit.

The standards are intended to help developers and Codex make consistent architectural decisions, including when implementing features that do not yet have an established project example.

The goal is not to minimize file count, line count, class count, or interface count. The goal is to keep responsibilities, dependencies, data ownership, and lifecycles understandable and controllable.

### 0.2 Scope

These standards apply to:

-   New systems and subsystems.
-   Existing systems when they are modified.
-   GDScript classes and functions.
-   Godot scenes and nodes.
-   Static game-content Resources.
-   Runtime business models.
-   Cross-system and cross-component communication.
-   Visual and audio presentation code.
-   Save data and serialization.
-   Editor tools and content-import pipelines.
-   Code, tests, and data generated by Codex.

### 0.3 Normative terms

The words below have specific meanings:

-   **MUST / MUST NOT:** Mandatory. A violation requires correction or an explicitly approved exception.
-   **SHOULD / SHOULD NOT:** Default recommendation. An exception is allowed when there is a concrete reason.
-   **MAY:** Optional technique that can be used when appropriate.

### 0.4 Project documents and source of truth

The project uses separate documents for separate purposes:

-   `AGENTS.md` defines the AI collaboration workflow and required reading.
-   `CODE_STANDARDS.md` defines code architecture and implementation rules.
-   `ARCHITECTURE.md` records the observed architecture and current implementation.
-   `CODEMAP.md` helps locate project files.
-   `GAME_DESIGN.md` records intended game rules and design decisions.

UI and visual-presentation tasks follow this standards document and the actual scene/script implementation. Do not assume a separate UI workflow document exists.

These documents are complementary; they must not be silently treated as interchangeable.

When documentation conflicts with actual source code, Codex MUST report the discrepancy and inspect the relevant implementation. It MUST NOT silently assume that either the documentation or the code is correct.

When implementation requirements conflict with an explicit game-design decision, Codex MUST stop and request clarification rather than inventing a compromise.

### 0.5 Draft standards versus accepted project patterns

The existence of code in the repository does not prove that the code is architecturally correct.

Existing code and architecture patterns MUST be treated as **unverified examples** until they have been reviewed and accepted by the project owner.

Use the following review states when documenting patterns:

-   **Draft:** Proposed design; not yet reviewed.
-   **Implemented:** Present in code; correctness not yet established.
-   **Reviewed:** Source has been inspected for the relevant responsibilities and dependencies.
-   **Tested:** Relevant behavior has been verified through appropriate tests or runtime checks.
-   **Accepted:** Explicitly approved by the project owner as a project-standard example.
-   **Deprecated:** No longer recommended for new work.

Codex MUST NOT describe an existing implementation as an accepted standard unless its status is confirmed.

## 1. System Architecture

### 1.1 System, Subsystem, and Component Definitions

A **System** is a bounded group of responsibilities that delivers a coherent game or application capability and exposes that capability through one public boundary.

A **Subsystem** is a bounded capability owned by one parent System. It has its own internal responsibilities and a defined interface to its direct parent, but it is not independently exposed to unrelated peer systems.

A System and a Subsystem follow the same internal architecture. Their difference is their ownership level and who is allowed to use their Entry:

-   A top-level System exposes its Entry to authorized peer Systems or the application-level coordinator.
-   A Subsystem exposes its Entry only to the Manager of its direct parent System or Subsystem.
-   A Subsystem MUST have exactly one direct parent in the System hierarchy.
-   A Subsystem MUST NOT be called directly by unrelated Systems or by sibling Subsystems.

A **Component** is a cohesive implementation unit inside a System or Subsystem. It performs a focused responsibility and does not establish an independent System boundary. A Component does not require its own Entry or System Manager.

A **Data Model** represents authored data, persistent state, runtime state, or a business concept. It is not automatically a System or Component coordinator.

A **Presentation Component** renders or communicates gameplay state. It does not own authoritative gameplay outcomes.

A System is not synonymous with a single script, scene, folder, or Manager.

When classifying a capability, consider:

-   Its business responsibility.
-   Whether it owns authoritative state.
-   Whether it has a meaningful lifecycle.
-   Whether it needs a stable boundary to its parent or peer Systems.
-   Whether it contains enough internal coordination to justify a Manager.

These are architectural judgment criteria, not a mechanical checklist. Do not create a System merely to reuse a helper function or to make the folder tree look symmetrical.

The System hierarchy is an **ownership tree**. The dependency graph between Systems may contain multiple directed dependencies, but it MUST NOT contain circular dependencies.

### 1.2 Required Structure: One Entry and One Manager

**MUST**

Every formal System and every formal Subsystem MUST have exactly:

1.  One **System Entry** script.
2.  One **System Manager** script.

These are separate scripts with separate responsibilities.

The Entry is the only business interface visible outside that System/Subystem boundary. The Manager is internal and MUST NOT be exposed as an external interface.

Recommended file naming:

-   `<system_name>_system.gd` for the Entry.
-   `<system_name>_manager.gd` for the unique System Manager.

The same convention applies to Subsystems.

A System or Subsystem MUST NOT have multiple competing Entry scripts or multiple peer System Managers for the same boundary.

This does not prohibit internal Components from having focused helper classes or controllers. However, names such as `XManager` SHOULD be reserved for the unique Manager of a formally defined System or Subsystem. Prefer responsibility-specific names such as `TimelineScheduler`, `CardPile`, `EntityRegistry`, or `DamageCalculator` for ordinary Components.

### 1.3 System Entry: The Boundary Adapter

The System Entry is the only business interface exposed outside its own boundary.

Its responsibilities are:

-   Receive structured Requests and approved queries.
-   Perform boundary-level validation, such as checking that a required request object exists and that its contract is usable.
-   Delegate business operations to its own System Manager.
-   Return the Manager's result through the public Result contract.
-   Expose approved read-only snapshots or queries.
-   Publish outward-facing business signals.
-   Relay or translate internal Manager events into the System's public Event contract.
-   Establish the references and signal connections required by the boundary, where appropriate.

For a top-level System, authorized peer Systems call its Entry.

For a Subsystem, only the Manager of its direct parent may call its Entry.

The Entry MUST NOT:

-   Implement the full business workflow itself.
-   Duplicate the Manager's coordination logic.
-   Perform low-level Component operations.
-   Own all authoritative data merely because it is the Entry.
-   Expose internal Manager or Component references.
-   Let external callers connect directly to internal Component signals.
-   Provide a shortcut to a nested Subsystem's internal Manager.

The Entry SHOULD remain a narrow boundary adapter. It may contain limited validation, translation, wiring, and lifecycle glue, but business workflows belong in the Manager and focused operations belong in Components.

Conceptual example:

``` gdscript
class_name BattleSystem
extends Node

signal battle_started(event: BattleStartedEvent)

var _manager: BattleManager

func start_battle(request: BattleStartRequest) -> BattleStartResult:
    if request == null:
        return BattleStartResult.invalid_request()

    return _manager.start_battle(request)

func _on_battle_started(event: BattleStartedEvent) -> void:
    battle_started.emit(event)
```

This is an illustrative boundary pattern, not a claim that the current project already implements it.

### 1.4 System Manager: The Internal Coordinator

Every formal System and Subsystem MUST have exactly one System Manager.

The Manager is the default internal coordination center.

Its responsibilities are:

-   Receive business operations delegated by the Entry.
-   Coordinate workflows that involve multiple Components.
-   Coordinate calls to direct child Subsystem Entries.
-   Manage System-level workflow state and transitions.
-   Initialize, connect, and shut down internal Components and child Subsystems where required.
-   Receive internal Component notifications and decide the next business action.
-   Combine internal results into the Result returned to the Entry.
-   Enforce ordering and consistency across multi-Component operations.

The Manager MAY own orchestration state, such as the current workflow phase or active operation identifier.

The Manager MUST NOT automatically own every piece of business data. Authoritative data remains owned by the Component or Data Model whose responsibility it represents.

The Manager MUST NOT:

-   Become a God Object containing all business calculations.
-   Duplicate the implementation of its Components.
-   Become a universal data store for unrelated state.
-   Expose internal Component references outside its boundary.
-   Be called directly by a parent System or peer System.
-   Force every trivial local helper call to pass through it.

The Manager coordinates work; it does not replace the work performed by the Components.

### 1.5 Recursive Subsystem Organization

A Subsystem follows the same Entry + Manager structure as a top-level System.

For example:

``` text
ExpeditionSystem/
├── expedition_system.gd
├── expedition_manager.gd
│
├── WorldSystem/
│   ├── world_system.gd
│   ├── world_manager.gd
│   └── Components/
│
└── BattleSystem/
    ├── battle_system.gd
    ├── battle_manager.gd
    │
    └── CardSystem/
        ├── card_system.gd
        ├── card_manager.gd
        └── Components/
```

The example illustrates recursive organization only. It does not declare that these exact boundaries or files already exist in the project.

The allowed boundary flow is:

``` text
External System
    |
    v
Parent System Entry
    |
    v
Parent System Manager
    |
    +----> Child Subsystem Entry
                 |
                 v
            Child Manager
                 |
                 v
            Child Components
```

Rules:

-   A parent Manager MUST use a direct child's Entry, never the child's Manager or internal Components.
-   A child Manager MUST use its own child Subsystems through their Entries.
-   A parent Entry MUST NOT bypass its Manager to call a child Subsystem's Manager.
-   A Component MUST NOT bypass its Manager to access a sibling Subsystem's internals.
-   A child Subsystem MUST NOT call back into its parent Manager through a direct reference. It reports upward through a defined Result or Event contract.
-   A child capability may be exposed to external Systems only when the parent Entry explicitly includes that capability in the parent's public contract.

A Subsystem SHOULD be promoted to a top-level System when it becomes an independently owned capability that must be consumed by multiple unrelated Systems. A shared technical capability may instead be classified as infrastructure when it does not own gameplay business responsibility.

### 1.6 Manager-Led Internal Component Communication

**MUST / SHOULD**

The System Manager is the default coordinator for internal business workflows, but it is not a mandatory relay for every Component call.

The default rule is:

-   The Manager coordinates workflows spanning multiple Components.
-   The Manager coordinates operations that cross Component ownership boundaries.
-   Components own and implement their focused responsibilities.
-   Components may collaborate directly when the conditions below are satisfied.

Direct Component-to-Component collaboration MAY be used when:

1.  Both Components belong to the same System or Subsystem boundary.
2.  The dependency is explicit and injected or otherwise clearly established.
3.  The collaboration is cohesive and understandable from the Components' responsibilities.
4.  The dependency direction is one-way and does not create a cycle.
5.  The call does not bypass the authoritative owner of the state being read or changed.
6.  The collaboration does not secretly coordinate a larger workflow that belongs in the Manager.
7.  The collaboration does not expose either Component to an external System or unrelated Subsystem.

Direct collaboration SHOULD be limited to focused operations between closely related Components. If multiple Components repeatedly coordinate a larger workflow, move that orchestration to the System Manager.

A Component MUST NOT directly modify another Component's authoritative state through public mutable fields or retained internal references. It must use the owning Component's explicit operation contract or ask the Manager to coordinate the change.

Use:

-   Direct method calls for known, explicit synchronous collaboration.
-   Signals for notifications, asynchronous events, and upward reporting.
-   Structured Request, Event, Result, and Snapshot packages for business-level data exchange as defined in Section 2.

Typical internal flow:

``` text
System Entry
    |
    v
System Manager
    |
    +----> Component A
    |          |
    |          +---- direct call ----> Component B
    |
    +----> Component C
               |
               +---- signal/event ---> System Manager
```

The Manager MUST remain the default coordinator without becoming a universal proxy or event bus.

### 1.7 System Dependency Rules

**MUST**

-   A top-level System may depend on another top-level System only through that System's public Entry.
-   A parent Manager may depend on a direct child's Subsystem Entry.
-   A parent Manager MUST NOT access a child's internal Manager or Components.
-   A Subsystem MUST NOT be directly consumed by unrelated Systems or sibling Subsystems.
-   A System MUST NOT modify another System's authoritative mutable state directly.
-   Circular System dependencies MUST NOT be introduced.
-   SceneTree paths MUST NOT be used to bypass a System boundary.
-   Autoload access MUST NOT be used as a shortcut around explicit System interfaces.

Within one System boundary, direct Component collaboration is governed by Section 1.6.

A dependency should be visible in the code and explainable from the business responsibilities.

### 1.8 Shared Infrastructure Services and Tools

Not every application-wide capability is a gameplay System.

A shared infrastructure service or tool MAY support multiple Systems without becoming a formal System. `SaveManager` is a persistence infrastructure service of this kind.

Such a service:

-   MUST have one narrow, explicit technical contract.
-   MUST NOT own gameplay rules or unrelated authoritative business state.
-   MUST NOT become a substitute for communication through System Entries.
-   MUST interact with Systems only through an explicitly defined infrastructure contract.
-   MUST have a clear application-level owner responsible for its initialization and lifecycle.

A `SaveModule` is a persistence adapter that implements the contract consumed by `SaveManager`. It is not a gameplay System, Subsystem, or second public business Entry.

The infrastructure exception does not weaken the System boundary rules. It permits a narrowly scoped technical integration; it does not permit `SaveManager` to inspect or control internal gameplay Managers.

### 1.9 Recommended System Composition and File Organization

A formal System or Subsystem SHOULD use the following logical organization:

``` text
<CapabilityName>/
├── <capability_name>_system.gd
├── <capability_name>_manager.gd
│
├── Data/                  # Optional
├── Components/            # Optional
├── Subsystems/            # Optional
│   └── <ChildCapability>/
│       ├── <child_name>_system.gd
│       ├── <child_name>_manager.gd
│       └── ...
├── Presentation/          # Optional
└── Tests/                 # Optional
```

Only the Entry and Manager scripts are mandatory for a formal System or Subsystem. Other folders MUST be created only when they contain a real responsibility.

Additional rules:

-   A dedicated `.tscn` is not mandatory for every System or Subsystem.
-   A System Entry may be attached to an appropriate scene root or composed through another explicit initialization mechanism.
-   Node, RefCounted, Resource, and scene choices MUST follow actual lifecycle and ownership requirements.
-   Data contracts and models SHOULD be grouped where they are easiest to locate and maintain.
-   Presentation may be composed inside the owning System or as a dedicated presentation component/subsystem when its complexity justifies it.
-   Do not create empty folders, placeholder Managers, or wrapper scenes solely to satisfy a directory template.
-   Existing projects MAY retain established paths and names until a scoped refactor is approved. The Registry audit MUST record the actual paths rather than assume the recommended layout has already been adopted.

Architecture quality is determined by clear ownership and boundaries, not by folder symmetry or the number of files.

## 2. Data Exchange and Data Contracts

### 2.1 Structured packages for business communication

**MUST**

Business communication across System boundaries and business-level data exchange between Components inside one System or Subsystem MUST use structured data packages.

This rule applies regardless of whether the receiving operation is invoked through the Manager or through an allowed direct Component-to-Component call under Section 1.6. Manager-led coordination does not remove the package requirement for business data.

Do not spread one business request across a long list of unrelated positional parameters.

Not recommended:

``` gdscript
func start_battle(
    deck: Array,
    player_data: EntityData,
    enemy_id: int,
    difficulty: int,
    room_id: String
) -> bool:
    pass
```

Recommended:

``` gdscript
func start_battle(request: BattleStartRequest) -> BattleStartResult:
    pass
```

Example package:

``` gdscript
class_name BattleStartRequest
extends RefCounted

var deck: Array[CardInstance] = []
var player_data: EntityData
var enemy_id: int
var difficulty: int
var room_id: String
```

The package makes the business contract explicit and gives the request one stable identity as a unit.

Adding a field to a package can reduce changes to function signatures, but it does not remove the need to validate the field or update its consumers.

### 2.2 Package categories

Use package types that communicate the direction and meaning of the data.

#### A. Request

A Request represents an instruction or intention submitted to a system.

Examples:

-   `BattleStartRequest`
-   `CardTransferRequest`
-   `WeaponUpgradeRequest`
-   `RoomEnterRequest`
-   `PlayCardRequest`

A Request does not mean the requested operation has succeeded.

The receiving system MUST validate it and return an explicit acceptance or failure result.

#### B. Event

An Event represents a business fact that has already occurred.

Examples:

-   `BattleStartedEvent`
-   `CardPlayedEvent`
-   `EntityDamagedEvent`
-   `EntityDiedEvent`
-   `RoomEnteredEvent`

An Event MUST be emitted by the component or system that owns the authoritative fact.

Events MUST NOT be used to disguise commands or to let observers mutate the event producer's state.

#### C. Snapshot

A Snapshot represents a read-oriented view of state at a particular point in time.

Examples:

-   `BattleSnapshot`
-   `PlayerSnapshot`
-   `ExpeditionMapSnapshot`

A Snapshot is intended for display, inspection, or downstream calculation. It MUST NOT provide an indirect way to modify the original authoritative state.

#### D. Result

A Result represents the outcome of a request.

Use a typed result when callers need to distinguish multiple failure reasons or receive output data.

Examples:

-   `BattleStartResult`
-   `CardTransferResult`
-   `UpgradeResult`

A result MUST distinguish, where relevant:

-   Rejected before execution.
-   Accepted and completed.
-   Accepted but still in progress.
-   Failed during execution.
-   Cancelled.

Do not report an asynchronous operation as completed merely because it was accepted.

### 2.3 Package implementation

Packages SHOULD use explicit GDScript types.

Suitable implementations may include:

-   `RefCounted` classes for runtime request, event, snapshot, and result objects.
-   `Resource` classes when editor serialization or Resource references are useful.
-   Typed arrays and enums for constrained collections and choices.

A package SHOULD represent one coherent business concept.

Do not create:

-   A universal `GameData` package for unrelated operations.
-   A universal `Dictionary` contract with undocumented keys.
-   A package that contains unrelated data merely to avoid defining separate contracts.
-   A new package for every trivial local calculation.

### 2.4 When direct function parameters are allowed

The package rule applies to business communication, not every low-level function call.

Direct parameters MAY be used for local implementation details such as:

-   Pure mathematical calculations.
-   String or number conversion.
-   Small utility functions.
-   Private helper functions.
-   A simple local operation that does not cross a system or component business boundary.

Example:

``` gdscript
func calculate_damage(base_damage: float, multiplier: float) -> float:
    return base_damage * multiplier
```

A function MUST NOT evade the structured-package rule by being called a helper when it is actually a cross-component business interface.

### 2.5 Package validation

**MUST**

Every package contract MUST define:

-   Required fields.
-   Optional fields.
-   Field types.
-   Valid ranges or allowed values where applicable.
-   Default values, if a default is genuinely valid.
-   Reference validity requirements.
-   Ownership and mutability semantics.

Required fields MUST be validated before the receiving system performs an operation.

Do not silently replace missing game-design values with guessed values.

A missing required field is an invalid request or invalid content record, not an invitation to invent a default.

### 2.6 Ownership and reference semantics

Packaging data does not automatically copy it.

Every package MUST have an understood ownership model:

-   **Shared reference:** Both sides refer to the same object. Mutation rights must be explicit.
-   **Independent copy:** The receiver owns a separate copy.
-   **Read-only snapshot:** The receiver may inspect the data but must not mutate the authoritative source.
-   **Ownership transfer:** Responsibility for the object moves to a new owner.

Nested Arrays, Dictionaries, Resources, and object references require particular care. A shallow copy may still share mutable nested objects.

Do not rely on incidental reference-counting or container-copy behavior as a substitute for a business ownership decision.

### 2.7 No mutable implementation leakage

A system MUST NOT expose an internal mutable collection or internal manager when doing so would let callers bypass the system's rules.

Prefer a Snapshot or a specific Query result over returning an internal Array or Dictionary that callers can modify.

## 3. Logic and Visual Presentation

### 3.1 Core principle

**MUST**

Gameplay logic is authoritative. Visual and audio presentation responds to gameplay events.

The logic layer decides what happened. The presentation layer decides how that fact is shown to the player.

The logic layer MUST remain correct when animations, particles, sounds, camera effects, and other presentation features are disabled.

### 3.2 Responsibilities of the logic layer

The logic layer owns:

-   Rule validation.
-   Hit and miss decisions.
-   Damage and healing calculations.
-   Resource costs.
-   Status changes.
-   Entity state changes.
-   Card legality and card effects.
-   Action ordering and scheduling.
-   Victory, defeat, and other gameplay outcomes.
-   Emission of authoritative business events.

### 3.3 Responsibilities of the presentation layer

The presentation layer owns:

-   Character and object animations.
-   Visual effects and particles.
-   Audio playback.
-   Camera feedback.
-   Floating numbers and notifications.
-   UI transitions and visual state.
-   Presentation-specific timing and interpolation.

Presentation code MUST NOT decide gameplay outcomes or directly modify authoritative gameplay state.

### 3.4 Event-driven presentation

When a business event occurs, the logic system emits a signal carrying the corresponding structured Event package.

Example:

``` text
Battle Logic
    |
    | entity_damaged(event)
    v
Combat Presentation
    |
    +-- Play hit animation
    +-- Spawn impact effect
    +-- Play sound
    +-- Display damage number
```

The presentation layer SHOULD subscribe to events rather than poll internal logic objects or inspect their private state.

External systems MUST connect to signals exposed by the system entry script, not directly to internal component signals.

The entry script MAY relay an internal event after translating it into the system's public Event contract.

### 3.5 Presentation completion feedback

A presentation component MAY report that a presentation sequence has completed.

Example:

``` text
Battle Logic
    |
    | AttackEvent
    v
Combat Presentation
    |
    | PresentationCompletedEvent
    v
Battle Logic
```

This feedback may be used for pacing, sequencing, or deciding when the next presentation-dependent step can begin.

It MUST NOT determine whether the attack hit, how much damage it dealt, or whether the business event occurred.

The authoritative gameplay result MUST already be decided by the logic layer.

### 3.6 Presentation cancellation and failure

Any flow that waits for presentation MUST define what happens when:

-   The animation is interrupted.
-   The visual node is removed.
-   The scene changes.
-   The presentation component is disabled.
-   A callback never arrives.
-   A newer operation replaces the previous one.

The logic system MUST NOT become permanently blocked because a visual callback is missing.

Use operation identifiers or equivalent correlation data when callbacks can arrive late or out of order.

A timeout or cancellation fallback SHOULD exist for presentation-dependent waits.

### 3.7 Input and UI

UI and visual components MAY collect player input and convert it into a Request package.

They MUST NOT directly perform the authoritative business operation.

Example:

``` text
Combat HUD
    |
    | PlayCardRequest
    v
Battle Entry Script
    |
    | Validate and coordinate
    v
Card Logic
```

## 4. Game Content Authoring and Static Data Ownership

### 4.1 Content ownership

**MUST**

The project owner is the sole authority for defining and approving formal game content.

Codex is an implementation assistant. It may implement the data structures, tools, validation, import pipeline, and runtime behavior needed to support the content, but it MUST NOT independently decide the actual game content.

Formal game content includes, but is not limited to:

-   Card names, descriptions, categories, costs, damage, rarity, and effect configuration.
-   Enemy names, attributes, skills, action weights, and behavior configuration.
-   Weapon attributes, upgrade paths, and progression values.
-   Room definitions, encounters, rewards, and events.
-   Difficulty values, economy values, progression curves, and balance parameters.
-   Any other static value or configuration that materially affects player experience.

### 4.2 Codex permissions for content

Codex MAY:

-   Create or modify data schemas.
-   Add fields required by an explicitly requested mechanic.
-   Build Inspector extensions or editor tools.
-   Build importers and exporters.
-   Build validation tools.
-   Create isolated test fixtures and synthetic test data.
-   Mechanically enter or import content explicitly supplied by the project owner.
-   Report missing, inconsistent, or suspicious content values.

Codex MUST NOT, without explicit authorization:

-   Invent formal card, enemy, weapon, room, or other content records.
-   Choose gameplay balance values.
-   Change formal content values.
-   Rewrite descriptions or design intent.
-   Delete or replace formal content.
-   Generate production content based on guesses or similarity to existing records.
-   Fill missing gameplay values with invented defaults.
-   Move test content into production data.

If a requested implementation requires a new gameplay value or design decision that has not been supplied, Codex MUST identify the missing decision and ask the project owner.

### 4.3 Code defaults versus game-design defaults

A technical default is not automatically a valid game-design default.

Technical defaults MAY be used when they are safe and do not silently determine game behavior.

Examples:

-   An empty temporary collection.
-   A null optional reference.
-   A neutral internal initialization state.

Gameplay defaults such as damage, cost, cooldown, drop rate, rarity, action weight, or reward quantity MUST be explicitly designed or supplied by the project owner.

If a gameplay field is required, missing data MUST produce a clear validation error rather than a guessed value.

### 4.4 Static data and runtime behavior

Static data defines content and configuration. Code implements the rules that interpret and execute that data.

For example, a card definition may provide a damage value and an effect configuration. The code determines how the effect is validated and executed.

Codex MAY implement a new effect mechanism when the project owner specifies the intended behavior. Codex MUST NOT invent the effect's game-design values or intended player experience.

Do not hardcode production gameplay values in logic code merely to bypass the content data pipeline.

### 4.5 Content-authoring tools

**MUST**

The project MUST provide a practical way for the project owner to enter and maintain static game content.

Codex is responsible for implementing and maintaining the required tools.

Possible approaches include:

-   Godot Inspector and custom Resource inspectors.
-   Godot EditorPlugin tools.
-   Dedicated in-game or editor data-entry interfaces.
-   CSV or spreadsheet import.
-   Other structured authoring tools appropriate to the content.

The choice of tool SHOULD consider:

1.  Number of records.
2.  Number and complexity of fields.
3.  Nested effect or condition structures.
4.  Resource and asset references.
5.  Bulk editing requirements.
6.  Validation and error-reporting needs.
7.  The project owner's actual editing workflow.

Do not force the project owner to edit GDScript, raw Dictionary literals, or JSON text for routine content authoring when a suitable structured editor can be provided.

Do not build a large standalone editor before the actual data volume and editing needs justify it.

### 4.6 One authoritative source per dataset

**MUST**

Each formal dataset MUST have one authoritative editing source.

If CSV is the source of truth and `.tres` files are generated, the generated `.tres` files MUST NOT be treated as a second manual editing source.

If `.tres` files are the source of truth, an exported spreadsheet MUST NOT be edited and later imported as if it were authoritative unless that workflow is explicitly designed.

The pipeline MUST make clear:

-   Which files the project owner edits.
-   Which files are generated.
-   How generated files are rebuilt.
-   How import errors are reported.
-   How references and IDs are preserved.
-   How data changes are reviewed.

Do not create two-way editing workflows without a deliberate conflict-resolution design.

### 4.7 Static data validation

**MUST**

Formal content MUST be validated before it is used by the game.

Validation SHOULD cover, as applicable:

-   Required fields.
-   Field types.
-   Unique and stable IDs.
-   Numeric ranges and allowed enum values.
-   Valid Resource references.
-   Missing referenced records.
-   Supported effect types.
-   Required visual or audio references.
-   Invalid or contradictory combinations.
-   Duplicate records.
-   Unsupported schema versions.

Errors MUST identify the affected record and field wherever possible.

Validation MUST NOT silently rewrite content or adjust balance values.

### 4.8 Test data isolation

Codex MAY create synthetic data for tests.

Test data MUST:

-   Be clearly marked as test-only.
-   Be stored in a test-specific location or created inside test code.
-   Be excluded from production content loading.
-   Never overwrite formal content.
-   Never be presented as approved game design.

### 4.9 Content approval

Changes to formal content require project-owner approval.

Codex may propose content changes and explain their technical or balance implications, but the project owner makes the final decision.

When the project owner supplies content and explicitly requests mechanical entry or import, Codex may perform that operation faithfully without independently changing the supplied values or wording.

## 5. Data Types and Object Lifecycles

### 5.1 Type design criteria

**MUST**

Do not create a new class merely because several fields appear together.

Before creating a new data type, identify:

1.  What business concept does it represent?
2.  Who creates it?
3.  Who owns it?
4.  How long does it live?
5.  Which parts of its state may change?
6.  How does it relate to other types?
7.  How is it copied, converted, saved, restored, and destroyed?
8.  Does it need independent identity?

A type should exist because it represents a meaningful concept, lifecycle, identity, ownership boundary, or behavior---not merely to hold arbitrary fields.

### 5.2 Node

Use Node-derived classes for objects that need scene-tree participation, engine lifecycle, scene composition, input, or node-based behavior.

Typical responsibilities include:

-   System coordinators that are scene-owned.
-   Scene components.
-   Input handlers.
-   Character and world presentation nodes.
-   Components that interact directly with the SceneTree.

Do not use Node solely as a convenient container for ordinary business data.

### 5.3 Resource

Use Resource for:

-   Static content definitions.
-   Editor-authored configuration.
-   Reusable templates.
-   Resource references and asset configuration.

Examples may include:

-   `CardData`
-   `EnemyData`
-   `WeaponData`
-   `RoomData`

Godot Resources are mutable objects and may be shared by reference. Therefore, project code MUST treat shared static content Resources as read-only during normal gameplay.

Do not store one player's mutable instance state by modifying a shared template Resource.

### 5.4 RefCounted

Use RefCounted for:

-   Runtime business models.
-   Independent data objects that do not need scene-tree participation.
-   Temporary operation state.
-   Request, Event, Snapshot, and Result packages.
-   Models with a clear reference-counted lifetime.

Examples may include:

-   `CardInstance`
-   `RuntimeCard`
-   `WeaponInstance`
-   `ExpeditionPlayerData`

These names are examples of possible roles, not proof that existing implementations have been accepted.

### 5.5 Static definition, owned instance, runtime instance

A useful design pattern is to distinguish:

1.  **Definition:** What kind of thing is this?
2.  **Owned instance:** Which specific thing does a player or persistent owner possess?
3.  **Runtime instance:** What is the state of that thing during a particular execution context?

A conceptual card flow is:

``` text
CardData
    |
    | Create
    v
CardInstance
    |
    | Convert for a battle
    v
RuntimeCard
    |
    | Create an action
    v
CombatAction
```

Possible responsibilities:

**CardData** - Defines static card content. - Holds base configuration and authored effect definitions. - Does not hold the mutable state of one player's card.

**CardInstance** - Represents one specifically owned card. - Has a stable identity. - Holds persistent or long-lived instance modifications. - Can participate in save and restore.

**RuntimeCard** - Represents that card in one battle or runtime context. - Holds temporary battle state and effects. - May retain the source instance identity for traceability. - Must not mutate the source instance unless an explicit, owner-controlled write-back operation exists.

**CombatAction** - Represents one submitted or scheduled combat action. - Does not replace the card's persistent identity. - Has its own execution lifecycle.

This is a conceptual example only. The project's actual card architecture must be audited and accepted before it is treated as a reference implementation.

### 5.6 Conversion contracts

Every conversion between data types MUST define:

-   Which fields are copied.
-   Which fields remain shared references.
-   Which fields are recalculated.
-   Which identity values are preserved.
-   Which temporary values are discarded.
-   Whether any state can be written back.
-   Who owns the resulting object.
-   What happens if conversion fails.

Do not assume that similarly named fields have identical semantics across types.

Do not merge two types merely because their fields overlap.

Do not create duplicate types merely because their names differ.

### 5.7 Lifecycle ownership

Every runtime object MUST have an identifiable owner responsible for its lifecycle.

The owner is responsible for:

-   Creation or acceptance of ownership.
-   Valid state transitions.
-   Removal from owned collections.
-   Cancellation of associated work.
-   Serialization where applicable.
-   Release or cleanup.

An object MUST NOT outlive the business context that gives it meaning unless that lifetime extension is explicitly designed.

## 6. State Ownership and Mutation

### 6.1 One authoritative owner

**MUST**

Every mutable business state MUST have one authoritative owner.

Other systems and components may:

-   Read an approved Snapshot or Query result.
-   Submit a Request to the owner.
-   React to Events emitted by the owner.

They MUST NOT maintain competing authoritative copies or modify the owner's state directly.

### 6.2 Derived and cached state

Derived values and caches MAY exist, but they MUST be clearly identified as non-authoritative.

A cache must have a defined invalidation or refresh rule.

Do not allow a cached value to become a second source of truth.

### 6.3 Mutation through the owner

Mutations MUST pass through the object or system that owns the relevant state.

The owner is responsible for validating the mutation and maintaining invariants.

Do not expose mutable arrays, dictionaries, or objects when callers could bypass the owner's rules.

### 6.4 Shared mutable objects

Shared mutable objects SHOULD be avoided across system boundaries.

If sharing is necessary, document:

-   The authoritative owner.
-   Which participants may read.
-   Which participant may mutate.
-   How mutation is synchronized.
-   How the object is invalidated or released.

Do not share a mutable effect, modifier, buff, or configuration object between runtime entities unless shared consumption and mutation are explicitly intended.

------------------------------------------------------------------------

## 7. Interfaces, Commands, Queries, and Signals

### 7.1 Public interface categories

A system's public interface generally consists of three categories:

**Command:** Requests a business operation.

``` gdscript
func start_battle(request: BattleStartRequest) -> BattleStartResult:
    pass
```

**Query:** Reads information the system allows callers to access.

``` gdscript
func get_battle_snapshot(request: BattleSnapshotRequest) -> BattleSnapshot:
    pass
```

**Event:** Announces a business fact.

``` gdscript
signal battle_started(event: BattleStartedEvent)
signal battle_ended(event: BattleEndedEvent)
```

Use the project's structured package rule for business requests, queries that need contextual input, and emitted events.

A query that genuinely needs no input MAY be a parameterless method, such as `is_battle_active()`.

### 7.2 Interface necessity

**MUST**

Every public method and signal MUST have:

-   A clear business purpose.
-   A known or justified consumer.
-   Defined input and output semantics.
-   Defined failure behavior where applicable.
-   A clear relationship to the system's responsibility.

Do not expose internal methods merely because they exist.

Do not create speculative interfaces for hypothetical future features.

Do not replace clear business interfaces with universal methods such as:

``` gdscript
execute(action_name, data)
get_data(key)
set_data(key, value)
```

Such methods hide the real contract and weaken type checking.

### 7.3 Request acceptance versus completion

A request being accepted does not mean its work has completed.

For synchronous operations, return the completed result.

For asynchronous operations, return or publish an explicit accepted/in-progress state and later report completion, failure, or cancellation.

Names and result types MUST make this distinction clear.

### 7.4 Signal usage

Use signals to notify observers about events without requiring the observer to be called directly.

Use direct method calls for explicit synchronous collaboration between known components.

Do not convert every method call into a signal.

Do not use a signal as a hidden command channel when a direct request interface is more appropriate.

Signals crossing a system boundary MUST be exposed or relayed by the system's public entry script.

### 7.5 Signal payloads

Business signals SHOULD carry one structured Event package rather than many unrelated positional arguments.

Presentation completion signals MUST include enough correlation information to identify the operation they complete when overlapping or delayed operations are possible.

------------------------------------------------------------------------

## 8. Dependencies and Global Services

### 8.1 Explicit dependencies

Business models SHOULD receive required dependencies through constructors or explicit initialization methods.

Avoid having ordinary RefCounted models discover their dependencies through:

-   Autoloads.
-   SceneTree searches.
-   Hard-coded node paths.
-   Other systems' internal managers.
-   Hard-coded resource paths when a reference can be supplied.

### 8.2 Autoloads

Autoloads SHOULD be reserved for genuinely application-wide services or registries.

Do not use Autoloads as a universal dependency locator.

A global service does not remove the need for a clear ownership and interface contract.

`SaveManager` MAY be provided as an Autoload when the application requires one shared persistence service. This does not make it a formal gameplay system, and it MUST NOT become a general-purpose access point for gameplay state.

### 8.3 Static registries and content databases

Static content registries MAY provide lookup access to authored definitions.

They MUST NOT become an excuse for runtime models to depend on unrelated global systems.

Content lookup and mutable runtime ownership are separate responsibilities.

------------------------------------------------------------------------

## 9. Lifecycle and Asynchronous Operations

### 9.1 Lifecycle definition

Every non-trivial operation MUST have a clear lifecycle.

For asynchronous operations, define:

-   Request creation.
-   Operation identity.
-   Start conditions.
-   Completion conditions.
-   Failure conditions.
-   Cancellation conditions.
-   Timeout or fallback behavior where needed.
-   Cleanup and ownership release.

### 9.2 Correlation identifiers

Use an operation ID, execution ID, request ID, or equivalent identity when:

-   Multiple operations can overlap.
-   Callbacks can arrive late.
-   A scene can be replaced during an operation.
-   A previous operation can be cancelled and restarted.
-   Completion events must be matched to a specific request.

A callback from an old operation MUST NOT mutate the state of a newer operation.

### 9.3 Cancellation

Cancellation MUST be explicit where an operation can outlive its owner or context.

Examples include:

-   Scene transitions.
-   Battle termination.
-   UI closure.
-   Replaced requests.
-   Destroyed runtime entities.

Do not assume that removing a Node automatically cancels every Callable, signal callback, timer, or external operation associated with it.

### 9.4 Timelines and presentation waits

If gameplay progression waits for presentation, the logic owner must control the wait state.

The presentation layer reports completion; it does not own the timeline or decide the business result.

Missing callbacks MUST have a defined recovery path so that the game cannot remain permanently blocked.

## 10. Error Handling and Validation

### 10.1 Explicit outcomes

**MUST**

Important business operations MUST expose success and failure explicitly.

Choose an outcome type appropriate to the operation:

-   `bool` for a simple success/failure distinction.
-   An enum result for multiple known business outcomes.
-   A typed result object when additional output or failure context is required.

Example:

``` gdscript
enum Result {
    SUCCESS,
    INVALID_STATE,
    INSUFFICIENT_RESOURCE,
    INVALID_TARGET
}
```

Do not use logging as a substitute for a return value or result event.

### 10.2 Errors, warnings, and expected rejection

Use:

-   A normal result for expected business rejection.
-   `push_warning()` for recoverable or degraded conditions that need developer attention.
-   `push_error()` for serious implementation or configuration problems.
-   `assert()` for development-time invariants that should never be false in a valid execution.

Do not treat an invalid player action as an engine error unless it indicates a real implementation defect.

### 10.3 Assertions

Assertions MUST NOT be the primary mechanism for validating ordinary external input or recoverable runtime conditions.

Required dependencies and content MUST be checked through explicit validation paths when their absence can occur in normal execution or production data.

### 10.4 Initialization failure

Initialization MUST have explicit success criteria.

If a required dependency is missing:

-   Initialization must fail.
-   The caller must receive the failure.
-   Partially created state must be cleaned up where necessary.
-   The system must not report itself as ready.

Optional dependencies MAY use a documented fallback.

### 10.5 No silent recovery that changes game design

A fallback MUST NOT silently invent gameplay values or alter authored content.

Technical recovery is allowed only when it preserves the intended game-design meaning.

## 11. GDScript Style and Code Organization

### 11.1 Naming conventions

New files SHOULD follow Godot's conventional naming style.

  Element           Convention           Example
  ----------------- -------------------- ---------------------
  Script filename   `snake_case`         `battle_manager.gd`
  Scene filename    `snake_case`         `combat_hud.tscn`
  Class name        `PascalCase`         `BattleManager`
  Function          `snake_case`         `start_battle`
  Variable          `snake_case`         `current_health`
  Private member    Leading underscore   `_current_state`
  Constant          `UPPER_SNAKE_CASE`   `MAX_HEALTH`
  Signal            `snake_case`         `battle_started`
  Enum type         `PascalCase`         `BattleState`
  Enum member       `UPPER_SNAKE_CASE`   `VICTORY`

Existing files MUST NOT be mass-renamed merely to make naming consistent.

Before renaming, inspect script references, scene references, resource paths, UID usage, and serialized data.

### 11.2 Static typing

**SHOULD**

Use explicit types for:

-   Public function parameters.
-   Public function return values.
-   Important member variables.
-   Typed collections.
-   Data package fields.
-   State enums and result values.

Prefer:

``` gdscript
var cards: Array[CardInstance] = []

func get_card(card_id: int) -> CardInstance:
    pass
```

Use `Variant` only when dynamic typing is genuinely required and its validation is clear.

### 11.3 Function responsibilities

Each function SHOULD perform one coherent operation.

Split complex logic into private helpers when doing so clarifies responsibilities or makes validation easier.

Do not split code merely to reduce line count.

Function names MUST accurately describe behavior.

In particular:

-   `get_*` SHOULD read without mutating authoritative state.
-   `is_*` SHOULD answer a condition without side effects.
-   `request_*` SHOULD make clear that the operation is a request, not guaranteed success.
-   `create_*` SHOULD make object creation and ownership clear.
-   `clear_*` SHOULD make the affected scope clear.
-   `initialize_*` SHOULD have explicit readiness and failure semantics.

### 11.4 Comments and documentation

Use `##` documentation comments for classes and public APIs where the purpose or contract is not self-evident.

Use ordinary `#` comments to explain non-obvious implementation decisions.

Comments SHOULD explain why a constraint exists, not merely repeat what the next line does.

Update comments when behavior changes.

### 11.5 One main responsibility per script

A script SHOULD have one primary responsibility.

Prefer one main class per script.

Inner classes MAY be used for tightly related implementation details that do not need independent reuse or lifecycle.

Do not split a script solely because it has many lines.

### 11.6 Avoid unnecessary abstraction

Do not add an interface, base class, factory, strategy object, manager, or service without a concrete design reason.

Abstraction is justified when it reduces real coupling, isolates a changing responsibility, enables meaningful reuse, or defines a stable contract.

Do not introduce abstraction only because a pattern is common in other projects.

## 12. Scene and Resource Organization

### 12.1 Scenes

Scenes should represent meaningful node compositions, reusable visual components, or objects with their own scene lifecycle.

Extract a component into a separate scene when it has:

-   Independent reuse value.
-   A meaningful lifecycle.
-   A coherent visual or interaction responsibility.
-   A clear ownership boundary.

Do not create a separate scene for every trivial Label, icon, or decorative node.

### 12.2 Node references

Prefer explicit exported references, dependency injection, or stable scene-local references when appropriate.

Avoid fragile deep relative paths when the same dependency can be expressed more clearly.

When modifying a scene hierarchy, inspect all affected node paths, signal connections, ownership relationships, and scripts.

### 12.3 Static versus runtime Resources

Static content Resources should be treated as shared definitions.

Runtime state belongs in runtime models unless a Resource is deliberately designed to be a unique runtime-owned object.

Do not modify a shared Resource at runtime to represent one entity's temporary state.

### 12.4 Generated Godot files

Do not manually edit generated import metadata, cache data, or UID metadata unless a specific maintenance task requires it and the implications are understood.

Do not commit temporary editor or import artifacts as source content unless the project explicitly requires them.

## 13. Persistence and Serialization

### 13.1 Persistent data is not the same as runtime data

Save data and runtime objects have different responsibilities.

A runtime Node, RefCounted object, Resource, or scene instance MUST NOT be assumed to be directly suitable for long-term serialization.

Define explicit save representations when runtime objects contain:

-   Scene references.
-   Callables.
-   Signals or connection state.
-   Temporary effects.
-   Runtime-only caches.
-   Engine objects.
-   References to other live objects.

### 13.2 SaveManager is shared persistence infrastructure

`SaveManager` is a shared infrastructure tool/service, not a gameplay system.

It MUST own only persistence-wide responsibilities, such as:

-   Save-slot and save-file lifecycle.
-   Registration and lookup of `SaveModule` instances.
-   Save-envelope metadata and format version.
-   Coordinating module validation and data collection.
-   Serialization orchestration.
-   File reading and writing.
-   Temporary-file handling and safe file replacement.
-   Coordinating load, migration, and recovery.

`SaveManager` MUST NOT:

-   Own gameplay state or implement system-specific gameplay rules.
-   Know the internal fields or serialization details of individual gameplay systems.
-   Read or modify another system's internal Manager, Component, Node, or SceneTree path.
-   Decide when a gameplay milestone should trigger a save.
-   Let a `SaveModule` write files directly.
-   Act as a general-purpose data bus or global state container.

`SaveManager` MUST interact with registered modules only through the `SaveModule` contract.

### 13.3 Optional SaveModules and registration

A `SaveModule` is a persistence adapter for a defined persistent data ownership boundary.

A system MAY provide a `SaveModule` when it owns data that must survive the relevant save/load lifecycle. Not every system requires one.

The persistence boundary MUST follow data ownership and lifecycle, not folder structure or the existence of a Manager.

A module MAY cover more than one closely related data model when those models share the same authoritative owner and persistence lifecycle. Unrelated data MUST NOT be grouped merely to reduce the module count.

Each registered module MUST define:

-   A stable, unique module key.
-   The save scopes it supports.
-   A schema version for each supported scope.
-   Which persistent data it is responsible for.
-   Its validation and restoration behavior.

The application-level save configuration MUST declare the required module keys for each save scope. A missing required module MUST fail the operation. An optional module MAY be absent only when the save contract explicitly defines how its data is safely omitted or reconstructed.

Registration MUST be performed by the application composition root or an explicitly designated owning coordinator. A module MUST NOT self-register by searching the SceneTree or discovering global managers.

Duplicate module keys MUST be rejected. Registration changes MUST NOT occur during an active save/load transaction.

A `SaveModule` MUST NOT:

-   Read or write save files directly.
-   Trigger a global save operation from inside serialization.
-   Call `SaveManager.save_game()` as part of `get_save_data()` or load logic.
-   Access unrelated systems or their internal managers.
-   Maintain a competing mutable copy of state owned elsewhere.

A module MAY own the authoritative persistent model when that ownership is explicitly assigned to it. Otherwise, it MUST obtain snapshots and request restoration through the owning system's approved public persistence contract or an explicitly injected persistence interface.

The module's persistence interface MUST NOT become a second general business entry point for the system.

### 13.4 Save scopes: Profile and Checkpoint

The project persistence model defines two distinct scopes.

#### A. Profile

`PROFILE` represents long-lived player or account progression that persists independently of one expedition run.

Examples may include:

-   Player-owned weapons and card instances.
-   Persistent deck configuration.
-   Permanent unlocks and progression.
-   Other player-owned data explicitly designated as long-lived.

The exact fields remain subject to game-design decisions.

#### B. Checkpoint

`CHECKPOINT` represents the latest successfully committed, approved recovery point for an active expedition.

It MUST contain enough authoritative data to reconstruct the game at that approved point. It is not automatically a complete copy of every live runtime object.

A module MAY support `PROFILE`, `CHECKPOINT`, or both. Its payload and schema version MUST be explicit for each supported scope.

Profile data and checkpoint data MUST have separate logical identities and lifecycles. Writing one scope MUST NOT accidentally overwrite, invalidate, or consume the other.

A save operation MUST state which scope it is operating on. A module that does not support the requested scope MUST NOT be called as if it did.

The following is an illustrative logical envelope, not a requirement for one physical file layout:

``` json
{
  "format_version": 1,
  "profile": {
    "modules": {
      "player": {
        "schema_version": 1,
        "data": {}
      }
    }
  },
  "checkpoint": {
    "run_id": "stable-run-id",
    "checkpoint_id": "stable-checkpoint-id",
    "modules": {
      "expedition": {
        "schema_version": 1,
        "data": {}
      }
    }
  }
}
```

The actual module keys, fields, and storage layout MUST be defined by the implementation and its approved data contracts.

### 13.5 Save timing belongs to the application workflow

The application-level coordinator or an explicitly designated workflow owner decides when a save should occur.

Examples of possible save boundaries include:

-   Completing a player loadout edit.
-   Entering or leaving an expedition.
-   Completing an approved expedition milestone.
-   Reaching a designed checkpoint.
-   Completing a result or settlement flow.

These are examples of possible boundaries, not a decision that every listed event must always save.

A gameplay system MAY publish an Event or completed Result indicating that a persistence boundary has been reached. The application coordinator decides whether to request a save and which scope to use.

`SaveManager` MUST NOT infer save timing from arbitrary state changes. A `SaveModule` MUST NOT independently decide to commit a global save.

Automatic saving on every mutation MUST NOT be introduced without an explicit autosave policy, including its consistency and performance implications.

### 13.6 SaveModule contract

Every `SaveModule` MUST implement the semantics below. Exact method signatures SHOULD remain consistent across modules.

Conceptual scope definition and interface:

``` gdscript
enum SaveScope {
    PROFILE,
    CHECKPOINT
}

func get_module_key() -> StringName:
    pass

func supports_scope(scope: SaveScope) -> bool:
    pass

func get_schema_version(scope: SaveScope) -> int:
    pass

func can_save(scope: SaveScope) -> bool:
    pass

func get_save_data(scope: SaveScope) -> Dictionary:
    pass

func validate_save_data(
    scope: SaveScope,
    data: Dictionary,
    schema_version: int
) -> bool:
    pass

func load_save_data(
    scope: SaveScope,
    data: Dictionary,
    schema_version: int
) -> bool:
    pass

func clear_data(scope: SaveScope) -> void:
    pass
```

The interface has the following requirements:

-   `get_module_key()` MUST return a stable key that does not change between application versions without an explicit migration.
-   `supports_scope()` MUST accurately describe supported scopes.
-   `get_schema_version()` MUST return a positive, explicitly managed version for that scope.
-   `can_save()` MUST be read-only and MUST reject incomplete or invalid authoritative state.
-   `get_save_data()` MUST return a consistent snapshot and MUST NOT mutate gameplay state.
-   `validate_save_data()` MUST validate data without mutating authoritative runtime state.
-   `load_save_data()` MUST return an explicit success/failure result.
-   `clear_data()` MUST clear only the module's owned in-memory data for the requested scope. It MUST be safe to call repeatedly.

`clear_data()` does not delete files or save slots. On-disk deletion is a `SaveManager` responsibility and MUST be an explicit operation.

The returned payload MUST contain only data that the configured serializer can represent. It MUST NOT contain live Nodes, Callables, signal connections, or arbitrary runtime object references.

A module MUST NOT mutate gameplay state while creating a save snapshot. The snapshot MUST represent one coherent logical point in time. If relevant state is changing asynchronously, the owning workflow MUST wait for a safe boundary, reject the save, or use an explicitly designed snapshot mechanism.

### 13.7 Coordinated save transaction

A save operation MUST be treated as one coordinated transaction for its requested scope.

The normal sequence is:

1.  Confirm that no conflicting save/load transaction is active.
2.  Resolve the registered modules required for the requested scope.
3.  Confirm that all required modules are present and support the scope.
4.  Call `can_save()` for every participating module.
5.  Collect each module's snapshot.
6.  Validate module keys, schema metadata, and serializer compatibility.
7.  Build the complete save envelope.
8.  Write to a temporary file.
9.  Flush and safely replace the previous committed file using the safest supported platform operation.
10. Report success only after the new save is committed.

If any required module fails validation or snapshot creation, the transaction MUST fail without committing a partial save.

The previously committed valid save MUST remain recoverable if the new write or replacement fails. Where the platform cannot guarantee safe replacement, an explicit backup/recovery strategy MUST be used.

Modules participating in one transaction MUST represent the same logical save boundary. They MUST NOT silently capture incompatible moments in time.

Only one conflicting save/load transaction MAY run at a time. Requests received during a transaction MUST be rejected, queued, or coalesced according to an explicit policy; they MUST NOT interleave file writes.

### 13.8 Coordinated load and restore transaction

Loading MUST be coordinated by `SaveManager`; modules MUST NOT independently load files.

The load sequence MUST:

1.  Read the selected save without overwriting it.
2.  Parse and validate the save envelope.
3.  Check the global format version.
4.  Resolve required module keys and module schema versions.
5.  Migrate supported old payloads using explicit migration rules.
6.  Validate every required module payload before applying any of them.
7.  Restore modules through an explicit, deterministic process.
8.  Report success only when the requested scope has been restored.

A module MUST NOT rely on incidental registration order. If restoration depends on another module, that dependency and restore order MUST be explicitly defined.

Validation SHOULD construct or stage the state needed for restoration without mutating the currently active authoritative state.

If applying a validated payload can still fail, the module MUST be able to roll back its own partial changes or provide a staged replacement. The overall load operation MUST NOT silently leave the application in a partially restored state.

A failed load MUST preserve the original save file. The application MUST remain in its previous valid state or enter an explicitly designed safe recovery state.

### 13.9 Checkpoint boundaries and recovery guarantees

A checkpoint is a recoverable business-state snapshot, not merely a flag indicating that an expedition was active.

The application and game design MUST define approved checkpoint boundaries. A checkpoint MUST be created only when the state required for restoration is internally consistent.

A checkpoint MUST include enough information to reconstruct the approved recovery point, including stable identities, progression position, and all authoritative state required by the supported recovery scope.

A checkpoint SHOULD include a stable run identifier, checkpoint identifier, and creation metadata. These values identify the recovery record; they MUST NOT replace the authoritative gameplay payload.

If an active run was created from profile-owned data that can later change, the checkpoint MUST preserve the exact run-entry snapshot or a stable immutable version reference needed to reconstruct that run. It MUST NOT assume that the player's current profile data will always recreate the same expedition state.

A checkpoint MUST NOT claim to restore a state that it does not save. For example, restoring in the middle of a battle requires an explicit design for the battle state that affects future outcomes, such as entities, resources, card/runtime state, and pending action scheduling. If that state is not serialized and validated, the checkpoint boundary MUST be placed outside that battle state.

The checkpoint policy MUST define:

-   Which gameplay boundaries create a checkpoint.
-   Which systems and modules participate.
-   What state is authoritative and must be saved.
-   What can be reconstructed from static content and stable IDs.
-   What happens when checkpoint creation fails.
-   When a checkpoint is replaced, consumed, invalidated, or deleted.
-   What happens after death, extraction, abandonment, or a new run.

A newly created checkpoint MUST NOT replace the previous valid checkpoint until its complete transaction commits successfully.

A marker such as `expedition_active` or `was_expedition_active` is recovery metadata only. It is NOT a checkpoint and MUST NOT be treated as sufficient data to reconstruct a previous expedition.

The project adopts checkpoint recovery as a target capability. This does not require every system to implement checkpoint serialization immediately, nor does it imply exact frame-by-frame recovery.

### 13.10 Stable identity and serialization representation

Persistent objects MUST use stable identifiers where identity must survive save/load, copying, or scene transitions.

Do not use array position or current scene-tree position as a persistent identity unless that is explicitly the intended design.

Save payloads SHOULD store stable content IDs and instance state rather than duplicating entire static content definitions.

The restore process MUST resolve IDs against authoritative content databases and handle missing records explicitly.

Save representations SHOULD use primitive values, arrays, dictionaries, and other explicitly supported serialized forms. Runtime objects MUST be converted into explicit data representations before serialization.

### 13.11 Schema versions and migration

The save envelope MUST have a global format version.

Every module payload MUST have its own schema version. A module's schema version MUST be managed independently from unrelated modules.

`SaveManager` owns migration of the global save envelope. Each `SaveModule` owns migration of its own payload.

A migration MUST:

-   Declare the source and target versions.
-   Validate its input.
-   Preserve stable identities and relationships.
-   Avoid inventing gameplay values.
-   Avoid silently discarding player-owned data.
-   Fail explicitly when safe migration is impossible.

Migration SHOULD operate on a copy or staged representation. The original save MUST remain recoverable until the migrated save has been successfully validated and committed.

Unknown future versions MUST be rejected safely rather than parsed as if they were compatible.

### 13.12 Failure handling and save safety

A save failure MUST be reported explicitly. A caller MUST NOT treat a requested save as successful merely because the request was accepted.

If a scene transition, extraction, or other workflow requires a successful save as a precondition, that workflow MUST NOT commit until the save succeeds.

A failed checkpoint write MUST leave the previous valid checkpoint available.

A failed profile save MUST NOT corrupt or consume a valid checkpoint, and a failed checkpoint save MUST NOT corrupt or consume valid profile data.

Missing content, invalid references, incompatible versions, and corrupt payloads MUST produce explicit errors or recovery outcomes. They MUST NOT be silently replaced with guessed gameplay defaults.

### 13.13 Persistence verification

Persistence changes MUST be verified at the level appropriate to their risk.

Relevant tests SHOULD include:

-   Save/load round-trip for each supported scope.
-   Stable identity preservation.
-   Nested mutable data copy and ownership behavior.
-   Missing, duplicate, and unknown module keys.
-   Missing required fields and invalid references.
-   Old, current, and unsupported future schema versions.
-   Migration success and migration failure.
-   Corrupt or truncated save files.
-   Failure during temporary write or final replacement.
-   Failure of one module while other modules are valid.
-   Checkpoint recovery from every approved checkpoint boundary.
-   Confirmation that state after the checkpoint is not falsely presented as recovered.
-   Confirmation that profile and checkpoint data remain isolated.

A successful JSON parse MUST NOT be treated as proof that the game state was restored correctly.

### 13.14 Adoption and existing implementation status

This section defines the target persistence architecture for the project. It does not claim that every requirement is already implemented.

During the current test stage, persistence MAY be implemented incrementally. Existing save modules and APIs MUST be inspected before they are extended or replaced.

Codex MUST distinguish:

-   Implemented behavior.
-   Missing behavior.
-   Behavior verified by tests.
-   Behavior that remains a design target.

Do not perform a broad persistence rewrite merely to make existing code match the names or signatures in this section. Preserve working save compatibility and use the smallest safe migration path.

The existence of a profile save or an expedition-active marker MUST NOT be reported as proof that checkpoint recovery is implemented.

## 14. Testing and Verification

### 14.1 Verification must match the change

**MUST**

Every code change MUST receive verification appropriate to its impact.

Possible levels include:

1.  Source inspection.
2.  GDScript parse and static checks.
3.  Isolated model or unit tests.
4.  System initialization tests.
5.  Cross-component contract tests.
6.  Scene construction tests.
7.  Runtime gameplay tests.
8.  Editor and visual inspection.
9.  Export or release-build checks when relevant.

A static check does not prove runtime behavior.

A successful scene load does not prove gameplay correctness.

A passing model test does not prove visual presentation correctness.

### 14.2 Test data

Tests MAY use synthetic data created by Codex.

Test data MUST remain isolated from formal production content.

Tests SHOULD cover both successful and failed operations, including invalid packages and lifecycle edge cases.

### 14.3 Regression tests

When modifying a shared model or public contract, inspect all consumers and add or update regression tests for important behavior.

Prior one-off probes SHOULD be converted into repeatable tests when they protect important project behavior.

### 14.4 Honest reporting

Codex MUST report:

-   What was checked.
-   What passed.
-   What failed.
-   What could not be checked.
-   Which claims are based only on static inspection.
-   Which runtime or visual behaviors remain unverified.

Do not claim that a feature is fully verified when only part of its behavior was tested.

## 15. Codex Development Workflow

### 15.1 Required reading and inspection

Before modifying code, Codex MUST:

1.  Read the applicable `AGENTS.md`.
2.  Read this `CODE_STANDARDS.md`.
3.  Read relevant sections of `ARCHITECTURE.md`.
4.  Use `CODEMAP.md` to locate likely files.
5.  Identify the actual System Entry and System Manager, if the capability is classified as a formal System or Subsystem.
6.  Inspect relevant child Subsystem Entries, internal Components, data models, and their ownership.
7.  Inspect related scenes, Resources, and signal connections.
8.  Find and inspect affected consumers and call sites.

Do not assume a documented architecture is still accurate without checking the current source.

Do not assume that a similarly named class has the expected responsibility.

### 15.2 Design before implementation

Before adding a feature, determine:

-   Which system owns the capability?
-   Which System Entry receives the request?
-   Which System Manager coordinates the workflow?
-   Which Component or Data Model owns the authoritative state?
-   Which existing data types can be reused?
-   Which Request, Event, Snapshot, or Result packages are needed?
-   What is the lifecycle of every new object?
-   Does the feature change static content schema?
-   Does the project owner need to provide game-design values?
-   Which presentation events are required?
-   Which failure, cancellation, and recovery paths exist?
-   Which tests can verify the behavior?
-   Does the feature require `PROFILE` persistence, `CHECKPOINT` persistence, both, or neither?
-   If checkpointed, what is the approved safe boundary and what exact state is required to reconstruct it?
-   Which `SaveModule` owns the persistence adapter, stable key, and schema version?

For a small implementation-only change, this reasoning may remain concise.

For a change to system boundaries, data ownership, persistence, or content schema, Codex SHOULD present the proposed design and wait for approval before making the architectural change.

### 15.3 Prefer existing architecture, but do not blindly copy it

Reuse accepted project patterns where they fit.

Do not copy an existing implementation merely because it exists.

If the existing implementation has not been reviewed or accepted, treat it as a candidate to inspect, not as an unquestionable template.

If the existing architecture cannot support a new requirement without violating these standards:

1.  Identify the conflict.
2.  Explain why the current structure is insufficient.
3.  Propose the smallest reasonable extension.
4.  Identify affected systems and data contracts.
5.  Request approval when the change affects architectural boundaries.

### 15.4 Minimal and controlled changes

**MUST**

-   Make the smallest change that correctly implements the requested behavior.
-   Inspect all affected consumers before changing a contract.
-   Preserve stable IDs and ownership semantics.
-   Preserve save compatibility unless a migration is explicitly designed.
-   Avoid unrelated refactoring.
-   Avoid broad renaming.
-   Avoid speculative systems and interfaces.
-   Do not replace working code with a new abstraction without a demonstrated need.

### 15.5 Content-authoring restrictions

Codex MUST follow Section 4.

When implementation requires new formal game content, ask the project owner for the missing content.

Do not use invented production values to make a demo appear complete.

Test fixtures are allowed only when isolated and clearly identified as test data.

### 15.6 Completion report

After a task, report:

1.  Files created or modified.
2.  Systems and components affected.
3.  Public interfaces or data contracts changed.
4.  New data types and their responsibilities.
5.  Ownership or lifecycle implications.
6.  Whether formal content was changed.
7.  Validation and tests performed.
8.  Results and failures.
9.  Unverified behavior and remaining risks.

## 16. Exceptions and Architectural Decisions

### 16.1 Exception process

If a requirement cannot reasonably be implemented under these standards, Codex MUST NOT silently bypass the rule.

It must:

1.  Identify the specific rule that conflicts with the requirement.
2.  Explain why the current design cannot satisfy the requirement.
3.  Present the smallest viable exception.
4.  Explain the impact on system boundaries, dependencies, ownership, lifecycle, and testing.
5.  Obtain project-owner approval before implementing an architectural exception.

### 16.2 Record important decisions

Significant decisions SHOULD be recorded in the appropriate project document.

Examples include:

-   Creating or splitting a system.
-   Changing a public system contract.
-   Introducing a new data lifecycle.
-   Changing static content schema.
-   Changing persistence semantics.
-   Introducing a new cross-system communication mechanism.

Do not duplicate the full architecture document inside this standards document. This file defines rules; the architecture document records the actual system design.

## 17. Design Review Checklist

Before accepting a new system, component, data type, or cross-system feature, review the applicable questions.

### System boundary

-   [ ] Is the capability correctly classified as a System, Subsystem, Component, Data Model, Presentation component, or infrastructure service?
-   [ ] Does each formal System or Subsystem have exactly one Entry script and one System Manager script?
-   [ ] Does the Entry expose only the approved boundary contract?
-   [ ] Does the Manager coordinate internal workflows without owning every Component's state?
-   [ ] Does a Subsystem have exactly one parent?
-   [ ] Does a parent Manager access a child only through the child's Entry?
-   [ ] Are internal Components hidden from external Systems?
-   [ ] Are direct Component collaborations explicit, cohesive, one-directional, and within one boundary?
-   [ ] Are larger multi-Component workflows coordinated by the Manager?
-   [ ] Are dependencies one-directional and understandable?

### Data exchange

-   [ ] Are cross-system business exchanges represented by structured packages?
-   [ ] Are cross-component business exchanges represented by structured packages, including allowed direct Component calls?
-   [ ] Are direct Component collaborations limited to clear, one-directional relationships within one System boundary?
-   [ ] Are multi-Component workflows coordinated by the Manager?
-   [ ] Are required fields and types explicit?
-   [ ] Are ownership and copy/reference semantics clear?
-   [ ] Are mutable internals protected?

### Logic and presentation

-   [ ] Does logic own the gameplay result?
-   [ ] Does presentation react to business events?
-   [ ] Can the logic remain correct without visual effects?
-   [ ] Are presentation completion and cancellation handled safely?
-   [ ] Does UI submit requests rather than mutate authoritative state?

### Data and lifecycle

-   [ ] Does each new type represent a meaningful concept?
-   [ ] Is its creator and owner clear?
-   [ ] Is its lifecycle clear?
-   [ ] Are conversions and copies explicit?
-   [ ] Are shared Resources treated as read-only?

### Content authoring

-   [ ] Are formal content values supplied or approved by the project owner?
-   [ ] Is the authoritative editing source clear?
-   [ ] Are production and test data isolated?
-   [ ] Are required fields and references validated?
-   [ ] Are missing gameplay values reported rather than invented?

### Persistence and recovery

-   [ ] Is `SaveManager` treated as infrastructure rather than a gameplay system?
-   [ ] Does each `SaveModule` correspond to a real persistence ownership boundary?
-   [ ] Are module keys, supported scopes, and schema versions stable?
-   [ ] Is authoritative state owned by one model rather than duplicated between a system and its save adapter?
-   [ ] Are save timing and checkpoint boundaries decided by an application workflow?
-   [ ] Are `PROFILE` and `CHECKPOINT` data isolated?
-   [ ] Does each checkpoint contain enough data for the recovery guarantee it claims to provide?
-   [ ] Are all required modules validated before a save or load is committed?
-   [ ] Are failed writes and restores prevented from silently destroying the previous valid state?
-   [ ] Are schema migration and stable identity rules explicit?
-   [ ] Are round-trip, failure, migration, and checkpoint recovery tests appropriate to the change?

### Quality and verification

-   [ ] Are failure paths defined?
-   [ ] Are asynchronous operations cancellable and correlated?
-   [ ] Are affected consumers inspected?
-   [ ] Are relevant tests or runtime checks performed?
-   [ ] Are unverified behaviors reported honestly?

## 18. Final Design Principle

Architecture quality is not measured by the number of managers, interfaces, classes, folders, or lines of code.

A good design makes the following clear:

1.  What each System and Subsystem is responsible for.
2.  How its Entry and Manager divide boundary and coordination duties.
3.  How parent-child and peer-System dependencies are constrained.
4.  Which Components may collaborate directly and under what limits.
5.  Who owns each mutable state.
6.  How business data is exchanged.
7.  How long each object exists.
8.  Which layer decides gameplay outcomes.
9.  How the project owner authors and controls game content.
10. How persistent state is owned, serialized, and restored.
11. How correctness is verified.

Every system, component, interface, and data type MUST have a clear reason to exist.

Prefer the simplest design that preserves explicit responsibilities, stable boundaries, correct ownership, and manageable lifecycles.

**The project owner defines the game. Codex implements the systems and tools that make the defined game work.**
